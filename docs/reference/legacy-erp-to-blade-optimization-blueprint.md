> 对比对象：启云记旧 ERP（`https://cnnew.qiyunji.com/main.html`）与当前 BladeProject
>
> 结论日期：2026-09-02
>
> 文档性质：产品与业务架构决策参考，不代表文中所有建议已在 Blade 中实现

> **2026-09-03 基线校准**：本文最初基于订单重构前的代码快照撰写。当前分支已完成 `BE-1040`～`BE-1051`、订单专用追加式财务流水与三轮整改，并获得 `CODEX_APPROVED_FOR_RELEASE_PREPARATION`。因此本文关于“BE-1041 开工前”“订单重构尚未实施”的表述只保留为历史风险说明，不再作为回退或重建现有模型的指令。完整资金账户、AR/AP、跨单核销和采购付款另列后续财务演进任务。

## 1. 执行结论

Blade 不应照搬旧 ERP 的菜单、密集表单和“保存即自动审核”交互，但必须继承旧 ERP 已经成熟的三类能力：

1. **账务闭环**：业务单据、库存流水、应收应付、收付款、核销关系、资金流水和报表之间可以按单号互相追溯。
2. **事务纪律**：审核才过账，反审核要检查下游依赖，调拨必须双边平衡，预定转单必须保留来源及剩余数量。
3. **经营完整性**：采购、销售、退货、盘点、其他出入库、资金调拨、开票、打印、权限和经营报表不是孤立页面，而是一套相互校验的业务账。

Blade 当前更有优势的部分是：商品/SKU 精细模型、订单快照、库存预留和并发控制、订单与履约软解耦、租户隔离、细粒度权限设计、文件中心、Catalog、移动端和 Agent 接入。正确方向是：

> **保留旧 ERP 的业务完整性和可对账性，用 Blade 的独立状态、不可变流水、现代权限和任务化交互重新实现。**

在“完全接替旧 ERP”这个目标下，Blade 当前最大的产品缺口不是销售开单，而是：

- 完整采购与供应商应付；
- 独立的收款单、付款单、账户与资金流水；
- 原单级核销与预收/预付；
- 审核、过账、作废、冲销的统一事务框架；
- 退货/退款、调拨、盘点和其他出入库闭环；
- 业务事实到报表的逐单对账能力。

这些能力中，前四项属于 ERP 接替的 **P0 门槛**。如果没有它们，新系统可以是一个更好用的销售订单与库存工具，但还不能完整替代旧 ERP。

## 3. 旧 ERP 全功能审计总结

### 3.1 总体业务架构

旧 ERP 的核心链路如下：

```text
基础资料
  ↓
预定 / 采购 / 销售 / 库存业务单据
  ↓ 审核过账
库存数量账 + 商品收发流水 + 应收应付
  ↓
收款 / 付款 / 预收 / 预付 / 核销
  ↓
资金账户流水
  ↓
进销存、利润、欠款、现金与员工业绩报表
```

其本质是“单据驱动的多本账系统”：一张业务单据不只改变自己的状态，还可能同时改变库存账、往来账和资金账。报表是这些业务事实的汇总结果，而不是单独维护的一套数字。

### 3.2 已确认的功能范围

| 领域 | 已审计能力 | 对接替系统的意义 |
|---|---|---|
| 销售 | 销售预定、销售、销售退货、零售、零售退货、积分兑换、销售开票 | 从需求、成交、履约到售后的完整销售链 |
| 采购 | 进货预定、进货、进货退货、进货开票 | 不只是库存入库，还形成供应商应付及付款关系 |
| 库存 | 查询、调拨、盘点、其他出入库、组装拆卸、预警、批次、保质期、串码 | 覆盖日常纠偏、仓间流转和高级追踪 |
| 财务 | 应收、应付、收款、付款、预收、预付、核销、账户调拨、其他收支 | 把“订单金额”和“现金发生”分开管理 |
| 商品 | 分类、属性、单位、多单位、品牌、条码、货位、价格、套餐 | 适合服装批发和多规格商品 |
| 往来单位 | 客户分类/等级价/积分/应收；供应商分类/应付 | 支撑定价和往来账 |
| 组织 | 门店、仓库、职员、资金账户、业务员 | 数据归属、制单和业绩统计的组织基础 |
| 权限 | 菜单/动作权限、价格可见性、改价限制、七类数据范围 | 功能权限和数据权限彼此独立 |
| 输出 | 多业务打印模板、条码打印、字段配置、导出 | 适配仓库、门店、财务的线下协作 |
| 审计报表 | 操作日志、收发明细/汇总、进销存、利润、欠款、现金、业绩 | 支持追溯和经营决策 |

### 3.3 已确认的关键业务规则

1. 销售审核后，同一单号可对应商品出库、应收变化和销售收入资金流水。
2. 进货审核后，同一单号可对应商品入库、应付变化和进货支出。
3. 零金额进货仍可产生库存；业务方确认零金额是为防止工厂人员看到价格而采取的录入规避，不代表免费采购，因此旧库存数量和旧财务金额必须按不同可信等级迁移。
4. 调拨按同一单号生成等量调出和调入，企业总库存守恒。
5. 收付款保存原单欠款、已核销、未核销、本次核销，核销是独立关系，不只是修改余额。
6. 有收付款或核销依赖的业务单据不能直接反审核。
7. 盘盈和盘亏分别派生其他入库、其他出库，统一进入库存流水分类。
8. 预定单保留已转、未转数量与金额，支持部分转换而不是一次性关闭。
9. 开票状态至少区分无需开票、待开票、已开票，撤销开票不等于删除业务单据。
10. 成本和利润列受权限控制，页面、查询和导出都应遵循同一授权。

### 3.4 当前旧账套影响业务行为的开关

| 开关 | 当前值 | 风险或设计启示 |
|---|---|---|
| 自动审核 | 开启 | 保存会立即过账；应在 Blade 中拆成明确动作或至少显著提示影响 |
| 销售/进货自动补齐实收实付 | 开启 | 容易把部分收付误做全额；Blade 应默认保守并展示尾款 |
| 禁止零库存出库 | 关闭 | 旧系统可能允许负库存；Blade 应按租户策略控制并记录例外授权 |
| 批次、保质期、串码 | 关闭 | 页面存在不等于当前业务已使用；不应直接列为 Blade 首发必需 |
| 业务员、积分 | 关闭 | 属于条件型能力，不应阻塞 P0 接替 |
| 数量/价格精度 | 均为 2 位 | Blade 数量模型不能只使用整数 |
| 自动打印零售小票 | 开启 | 测试和生产都需要“预览”与“发送打印”分离 |
| 服装批发格式 | 开启 | 颜色×尺码矩阵、批量录入和打印版式具有实际价值 |

### 4.3 测试安全结论

- 旧账套仓库+门店容量已达 5，且已确认无法提升，因此不应删除、改名或复用原有仓库来制造测试空间。
- 继续在“御龙”测试会影响真实仓库流水，只适合数量和金额可完全回零、且逐批获批的最小闭环。
- 共享系统参数、字段设置、默认打印模板和原职员权限不适合在生产账套中测试。
- 零售自动打印已开启，确认打印助手及物理/远程目标前，不应保存零售测试单。
- 最合理的后续验证环境是旧系统的脱敏副本或 Blade 自己的可重置沙箱。

## 5. 旧 ERP 最值得“取其精华”的设计

### 5.1 独立单据与独立账本

旧 ERP 没有把销售单上的一个 `paid_amount` 当作完整财务系统。销售单表达交易价值；收款单表达现金发生；核销明细表达现金用于偿还哪笔应收；资金流水表达账户变化。

Blade 应保留这种分层：

```text
订单/采购单：发生了什么业务
库存流水：实物发生了什么变化
应收应付：还欠多少
收付款流水：实际收到或付出多少现金
核销关系：这笔钱结清了哪些原单
```

这比只在订单主表累计“已收金额”更能处理分次收款、一笔收款核销多单、多账户拆分、预收预付、退款和历史追溯。

### 5.2 审核即过账，反向操作先检查依赖

旧 ERP 把“草稿数据”和“已进入账本的业务事实”区分开。这个原则应保留，但交互需要升级：

- 保存草稿不影响任何账；
- 过账前展示库存、应收应付和现金影响预览；
- 过账动作必须原子完成；
- 已有下游依赖时阻止直接撤销；
- 纠错通过作废或冲销产生反向流水，不删除历史。

旧 ERP 在 T10 中提出“先删除收付款单”是正确发现依赖、错误处理依赖。Blade 应保留阻断判断，但改成“先冲销关联收款”并提供依赖导航，不能鼓励删除。

### 5.3 来源单据与转换余额

预定转销售、进货预定转进货时保留来源 ID、已转数量、剩余数量和转换记录。这一逻辑适合 Blade 的纸单、WhatsApp、Agent 草稿到正式订单链路。

建议统一增加：

- `document_relation(source_type, source_id, target_type, target_id)`；
- 明细级 `source_item_id`；
- `source_qty / converted_qty / remaining_qty`；
- 幂等键，防止重复转换；
- 转换时间线和逐次转换记录。

### 5.4 数量账、资金账和经营账分别守恒

旧 ERP 调拨不改变企业总库存，账户调拨不改变企业总资金，收付款核销不改变订单原始金额。这个“不同账本分别守恒”的思想应作为 Blade 自动化测试的不变量，而不是只测 HTTP 成功。

### 5.5 商品快照和历史安全

旧 ERP 报表可按商品、属性、仓库、客户、供应商和单据交叉追溯。Blade 已在订单明细中保存 SKU、商品、颜色、尺码、售价、成本和毛利快照，这是比读取当前商品资料更可靠的方向，应扩展到采购、退货、库存和财务单据。

### 5.6 功能权限与数据范围分离

“能做什么”和“能对哪些数据做”是两种权限。Blade 的菜单、按钮、字段、API 权限设计应继续向旧 ERP 的仓库、客户、供应商、账户、职员、门店数据范围补齐，并确保导出、Agent 和移动端同样执行后端授权。

### 5.7 统一业务分类驱动报表

旧 ERP 的商品收发汇总使用统一业务类型区分采购、销售、退货、调拨、盘点、组装和其他出入库。Blade 应让报表消费不可变的库存/财务事实，而不是分别从多个页面表做容易漂移的临时 SQL。

## 6. 旧 ERP 不应照搬、应在 Blade 中优化的部分

| 旧设计问题 | 实际风险 | Blade 优化方式 |
|---|---|---|
| 保存即自动审核 | 用户可能未意识到库存和资金已经变化 | 明确分开“保存草稿”和“确认过账”；如保留自动化，必须有影响预览及租户级开关 |
| 自动补齐全额收付 | 部分收付容易被误记为结清 | 默认不补齐；显示订单额、本次收付、累计收付、核销和尾款 |
| 反审核引导删除收付款 | 丢失审计轨迹，容易破坏账实一致 | 收付款只追加，错误记录用 `REVERSAL` 冲销，原记录永久保留 |
| 一个状态承载多种语义 | “已付款”可能被误认为订单已完成或已出库 | 分离草稿、审核/过账、收款、履约、发票、售后状态 |
| 大量全局开关 | 改一个参数可能改变全账套行为 | 配置版本化，记录修改人/时间；高风险配置需审批及生效预览 |
| 表单密集且隐藏默认值多 | 新手易误操作，后果直到保存后才发现 | 分步任务流、默认值显式化、异常字段就地解释、保存前影响摘要 |
| 删除入口广泛 | “删除”和“回滚业务事实”混淆 | 草稿可软删；已过账单据只允许作废/冲销，不允许物理删除 |
| 打印可能自动发送 | 测试或误触可能输出真实单据 | 预览、生成文件、发送打印机三步分离；默认关闭自动发送 |
| 字段设置是共享配置 | 测试和个性化可能影响所有人 | 租户模板 + 角色模板 + 个人视图分层，并提供恢复默认 |
| 仓库/门店数量受套餐限制 | 技术配额进入业务流程并阻断测试 | Blade 的订阅配额与业务数据解耦；提供沙箱资源和清晰用量页 |

## 7. Blade 当前能力与差距

### 7.1 当前已经优于旧系统或方向正确的能力

| Blade 能力 | 当前证据 | 价值 |

| SKU 类型与规格精度 | `NORMAL/DEFAULT/PLACEHOLDER`，颜色、尺码、SKU 快照 | 适应服装录单和待拆分规格，同时保护真实库存 |

### 7.3 当前代码审计中应尽快处理的风险

以下不是旧 ERP 对比推测，而是当前代码快照中可见的风险：

1. `OrderServiceImpl.updateStatus()` 仍可直接写任意数字状态，绕过统一动作白名单和副作用处理；这正是 BE-1042 要消除的入口。
2. `cancelOrder()` 注释和实现都明确“不涉及库存释放”。当前软解耦阶段可能成立，但一旦订单已建立预留或配货计划，取消必须由统一状态机清理依赖。
3. 当前追加收款直接累计订单金额快照，没有不可变的逐笔收款记录；无法可靠回答“谁在何时以哪个账户收了多少钱，以及哪笔已被冲销”。
4. `InventoryServiceImpl.out()` 在检查 `inv == null` 前先读取 `inv.getQuantity()`，无库存记录时可能抛出空指针而不是稳定的业务错误。该问题应作为库存异常路径测试项修复。
5. 当前 `OrderDeliveryServiceImpl` 和订单发货存在新旧出库入口兼容层；虽然最终委托到统一发货路径，但重构完成前仍需持续验证租户范围、幂等和重复出库。

## 8. 推荐的目标业务架构

### 8.1 不要做一张“万能单据表”

销售、采购、调拨、盘点和收付款具有不同的不变量，建议使用领域专用聚合和表结构，但共享以下基础协议：

- 草稿、过账、作废/冲销接口；
- 单号、租户、门店、业务日期、制单人、操作人；
- 来源单据关系；
- 幂等键；
- 附件和备注；
- 状态转换日志；
- 过账结果及影响摘要。

### 8.2 五个相互独立的状态维度

| 状态维度 | 示例 | 负责回答的问题 |
|---|---|---|
| 文档生命周期 | DRAFT / CONFIRMED / VOIDED | 单据是否有效存在 |
| 过账状态 | UNPOSTED / POSTED / REVERSED | 是否已经进入业务账本 |
| 收付状态 | UNPAID / PARTIAL / SETTLED | 现金及核销是否结清 |
| 履约状态 | WAITING / ALLOCATING / SHIPPED / COMPLETED | 实物走到哪一步 |
| 发票状态 | NOT_REQUIRED / PENDING / ISSUED / CANCELLED | 发票义务和执行情况 |

状态应由动作和事实计算，前端不能直接提交最终状态值。

### 8.3 一次过账的原子事务

以采购入库为例，一次成功过账应在同一事务边界内完成：

```text
锁定采购单并校验版本/幂等
  → 写库存入库流水与库存快照
  → 写供应商应付发生
  → 如有本次付款，写付款流水及核销关系
  → 重算采购单与供应商余额快照
  → 写状态转换和操作审计
  → 发布 outbox 事件供报表/通知消费
```

任一步失败，前面的数据库变化必须一起回滚。外部通知、打印和 Agent 回调通过 outbox 在事务提交后执行，不能影响核心账务提交。

### 8.4 只追加流水，禁止删除业务历史

建议新增或完成以下事实表：

- `inventory_ledger_entry`
- `receivable_entry` / `payable_entry`
- `cash_transaction`
- `payment_allocation`
- `order_financial_record`
- `document_relation`
- `business_state_transition_log`
- `business_action_audit_log`

错误事实使用引用原记录的 `REVERSAL` 冲销。主表余额和状态是可重算快照，流水才是真相。

### 8.5 报表统一消费业务事实

- 订单额按业务日期统计；
- 现金按收付款发生时间统计；
- 库存按实际出入库时间统计；
- 应收应付按发生、核销和冲销事实计算；
- 毛利使用订单/出库成本快照，不读取当前商品成本；
- 每个汇总数字都能下钻到单据和流水；
- 定时运行跨账本不变量检查，并把异常列入运营工作台。

## 9. 推荐的交互优化

### 9.1 过账前影响预览

在“确认过账”按钮上方展示：

```text
本次操作将：
御龙 / SKU-A       库存 +10
供应商 TEST-...     应付 +100
账户 A              现金 -40
剩余应付             60
```

这比通用弹窗“将操作库存和资金，是否继续”更能阻止误操作。

### 9.2 依赖阻断不只报错，还要给处理路径

若销售单有关联收款，撤销时应展示：

- 关联收款单号及金额；
- 已核销的原单关系；
- 允许动作：返回、发起冲销、申请财务审批；
- 无权限时显示需要哪个角色处理。

不能显示“是否先删除收款单”。

### 9.3 单据详情使用统一时间线

时间线合并展示：创建、修改、确认、收款、核销、配货、出库、退货、退款、作废、冲销、打印和导出。每条记录包含操作人、来源（PC/移动端/Agent）、前后状态和关联单号。

### 9.4 保留服装批发高效录单，改善可理解性

旧 ERP 的颜色×尺码、批量商品、多单位和服装打印格式具有价值。Blade 可保留矩阵录入和键盘操作，但增加：

- 未识别规格暂存为 `PLACEHOLDER`，进入库存履约前强制拆分；
- 固定显示本次数量、金额、库存可用量和异常；
- 快捷录入不绕过服务端校验；
- 大批量操作提供撤销预览和差异清单。

### 9.5 提供可重置沙箱

为测试租户提供：

- 测试仓库、账户、客户、供应商默认资料；
- 所有单据明显的“测试”水印；
- 禁止真实打印、短信和外部推送；
- 一键按测试批次归档或重置；
- 与生产完全隔离的编号和报表口径。

这可以从根本上解决旧账套容量、真实流水污染和共享配置不能测试的问题。

## 11. 接替验收标准

### 11.1 最小采购—销售—核销不变量

用隔离客户、供应商、账户、仓库和 SKU 完成：

1. 采购 10 件、部分付款；库存 +10，应付等于未付金额，现金减少实付金额。
2. 追加付款并核销；供应商应付归零，付款分笔可追溯。
3. 销售 10 件、部分收款；库存回到 0，应收等于未收金额，现金增加实收金额。
4. 追加收款并核销；客户应收归零，收款分笔可追溯。
5. 最终库存、应收、应付和资金满足守恒公式，且所有数字可下钻到流水。

### 11.2 撤销与冲销

- 已有收款的销售单不能直接撤销或删除。
- 冲销收款后保留原流水和反向流水，账户余额恢复。
- 作废销售必须生成库存和应收反向事实，不能覆盖原流水。
- 重复请求使用同一幂等键不会二次扣库存或二次收款。

### 11.3 并发与权限

- 同一 SKU+仓库并发出库不会超卖，也不会出现部分流水已写而订单失败。
- 无库存记录时返回稳定业务错误，不产生空指针异常。
- 无财务权限的用户、移动端或 Agent 看不到成本和账户，也不能通过直接 API 越权收款、核销或冲销。
- 数据范围权限同时约束列表、详情、下拉选项、导出和写接口。

### 11.4 报表对账

- 库存余额 = 期初 + 全部有效入库 - 全部有效出库。
- 应收余额 = 应收发生 - 收款核销 - 优惠/核销 + 有效冲销调整。
- 应付余额遵循对称公式。
- 账户余额 = 期初 + 有效收入 - 有效支出 ± 账户调拨。
- 调拨前后企业总库存/总资金不变。
- 报表汇总与逐单下钻合计完全一致。

## 12. 最终取舍清单

### 直接保留其原则

- 单据、库存、往来、现金和核销分层；
- 审核/过账的事务边界；
- 下游依赖检查；
- 预定部分转换及来源关系；
- 调拨守恒；
- 多维数据权限；
- 全链路报表下钻和对账。

### 保留业务价值但重新设计

- 反审核改为作废/冲销；
- 自动审核改为显式过账或带影响预览的自动化；
- 密集表单改为任务化工作台；
- 全局配置改为分层、版本化配置；
- 打印改为预览、生成、发送分离；
- 数字组合状态改为独立状态维度。

### 不建议复制

- 删除已发生业务记录；
- 用一个付款状态代表订单全过程；
- 默认全额收付且不突出尾款；
- 只在前端隐藏价格或按钮；
- 测试直接使用生产共享配置；
- 把订阅容量限制混入正常业务数据模型。

最终建议是：**以 Blade 已规划的订单生命周期和不可变财务流水为主架构，用旧 ERP 的采购、应付、收付款核销、库存专项和报表对账能力补齐业务范围。** 这样得到的不是旧系统复刻版，而是一套更安全、更可解释、可移动化和可被 Agent 使用的新 ERP。

## 13. 结合近期商品与订单更新后的具体改造方案

### 13.1 当前已完成能力应作为基础，不推倒重做

近期商品和订单改造已经形成以下可复用基础：

| 已有能力 | 当前状态 | 结合旧 ERP 后的处理决定 |
|---|---|---|
| 商品编辑 v2 | 已支持基础信息、颜色尺码、SKU 明细、商品素材分区维护 | 保留；在此基础上增加供应商关系、单位/品牌等必要主数据，不恢复旧 ERP 的超长单页 |
| SKU 精细维护 | SKU 可单独维护售价、成本、条码、状态和图片 | 保留；采购、销售、库存都必须引用同一真实 SKU，并保存历史快照 |
| SKU 三类型 | `NORMAL`、`DEFAULT`、`PLACEHOLDER` | 保留并强化业务边界；占位 SKU 只用于需求采集，永不成为库存事实 |
| 商品/SKU 素材 | 统一使用文件中心绑定、缩略图和 Catalog | 保留；采购和订单只引用文件，不复制图片字段体系 |
| 快速录单 SKU 矩阵 | 按商品选择颜色×尺码并批量写入明细 | 保留，作为人工高频录单主路径；库存只做软提示，不阻断录单 |
| Agent 订单草稿 | 独立草稿表、原始识别值、警告、幂等号、人工确认 | 保留；草稿不是正式业务账，也不能兼任旧 ERP 的销售预定单 |
| 订单/库存软解耦 | 收款不扣库存，发货按实际配货扣库存 | 保留；比旧 ERP 保存即过账更适合当前纸单和跨仓配货流程 |
| 订单新生命周期方案 | 收款、履约方式、履约状态已经拆分并通过终审 | 保留现有订单子账；后续财务扩展通过桥接/投影接入，不回退或重建订单状态机 |

因此本轮不再新做一套商品和订单页面，而是围绕这些已经稳定的主入口补业务账本和事务闭环。

### 13.2 商品模型的调整

#### 13.2.1 固化 SPU、真实 SKU、占位 SKU 三层边界

| 对象 | 允许承担的业务 | 禁止承担的业务 |
|---|---|---|
| 商品/SPU | 款号、商品名称、分类、品牌、商品级默认价格、素材、分析归集 | 不直接记录仓库库存和实际出库 |
| `NORMAL/DEFAULT` SKU | 采购、入库、库存、配货、出库、退货、盘点、批次/串码 | 不能被后续商品改名覆盖历史单据快照 |
| `PLACEHOLDER` SKU | 纸单或 Agent 只识别到款号时暂存需求；计入款号级订单分析 | 采购入库、库存余额、可售库存、配货、出库、盘点、批次和串码 |

人工快速录单与 Agent 草稿都可以明确选择“整款录入”；Catalog 继续排除占位 SKU。正式订单可以先选择 `STOCK_LINKED` 表达履约意图，但在创建配货计划、预留或出库前必须完成拆分。

占位拆分必须满足：

- 原占位数量 = 拆分到真实 SKU 的数量合计 + 剩余未拆数量；
- 销售金额、客户贡献和款号总销量不变；
- 真实颜色/尺码销量只在拆分完成后出现；
- 拆分前后明细、操作人、时间和来源永久可追溯；
- 重复提交不会重复增加真实 SKU 数量；
- 含剩余占位数量的订单可以记录 `STOCK_LINKED` 意图，但不能创建配货、预留或出库事实。

这部分直接复用现有 `BE-610`～`BE-612`、`BA-805`、`BE-1045` 和 `BA-1123`，不另建重复任务。

#### 13.2.2 供应商不能继续只是商品上的单一字段

当前 `product.supplier_id` 只能表达一个默认供应商，无法覆盖旧 ERP 的采购、供应商价格和往来账。建议：

- 保留 `product.supplier_id` 作为兼容期“默认供应商”投影；
- 新增 `supplier` 主数据；
- 新增 `supplier_product` 或 `supplier_sku` 关系；
- 关系记录供应商货号、采购单位、最近采购价、约定价、最小起订量、交期、是否默认；
- 采购单明细保存供应商货号、单位、采购价和商品/SKU 快照；
- 商品停用不能删除历史采购关系，供应商停用不能破坏应付和付款记录。

供应商关系属于采购域，不应继续塞入商品 v2 弹窗。商品页只展示和选择默认/可用供应商，完整往来资料在供应商模块维护。

#### 13.2.3 单位、品牌、属性按真实使用分层引入

旧 ERP 支持多单位、品牌和通用属性，Blade 当前核心模型更专注于颜色、尺码。建议顺序：

1. P1 增加品牌和规范化基础单位，替代自由文本造成的同义值。
2. 上线前只读扫描历史数据，确认是否实际存在小数数量、多单位换算和通用属性订单。
3. 如果实际业务始终按“件”交易，当前 P0 继续使用整数数量，避免在订单重构中夹带全库数量类型迁移。
4. 如果存在按箱/包/米/公斤交易，再单独实施单位换算，并统一把订单、采购、库存、盘点和报表数量升级为高精度十进制。
5. 通用属性只用于颜色/尺码以外确实影响 SKU、定价或筛选的维度；描述性信息优先放商品扩展资料，不把所有字段都组合成 SKU。

数量类型是跨订单、库存和报表的不可逆大改，必须由真实数据审计决定，不能因为旧 ERP 页面存在多单位就直接实施。

#### 13.2.4 建立明确的价格优先级

旧 ERP 有等级价、禁止改价和成本隐藏；Blade 有商品价、SKU 价和纸单识别价。建议统一为：

```text
订单实际成交价（人工/纸单确认）
  ↑ 只在有改价权限时可覆盖
客户专属价
  ↑
客户等级价
  ↑
SKU 默认售价
  ↑
商品默认批发价
```

无论价格来源如何，正式订单明细都保存最终成交价、价格来源、参考价和改价人。成本价单独保存快照并受字段/API/导出权限控制。旧 ERP 当前关闭“价格记忆”，Blade 第一版也不应静默沿用上一次成交价；如以后启用，应明确显示“最近成交参考”，不能自动覆盖默认价。

### 13.3 订单模型的调整

#### 13.3.1 草稿、预定、正式订单必须分开

近期新增的 `order_draft` 解决的是“外部数据尚未核对”，旧 ERP 的销售预定解决的是“客户已经形成业务承诺、可能已收定金、等待后续转单”。两者不能共用状态：

| 对象 | 是否进入经营统计 | 是否产生应收/收款 | 是否影响库存 | 后续动作 |
|---|---|---|---|---|
| 识别草稿 | 否 | 否 | 否 | 校对、匹配、确认生成正式订单 |
| 销售预定 | 按预定统计，不计正式销售 | 可记录独立定金/预收 | 默认不影响实际库存，可选软承诺 | 部分或全部转正式订单，保留转换余额 |
| 正式销售订单 | 是 | 形成应收并接受核销 | 仅 `STOCK_LINKED` 实际出库时影响 | 收款、履约、退货、退款、作废/冲销 |

当前 `order_type=PREORDER` 只是标签，不能替代旧 ERP 的预定转换模型。如果实际业务需要部分转单，应后续新增独立 `sales_preorder` 聚合和明细级转换关系，而不是不断给正式订单加特殊状态。

#### 13.3.2 草稿确认必须一次完成业务交接

确认 Agent 草稿时，在同一事务内完成：

1. 锁定草稿，检查租户、状态和幂等号；
2. 校验客户、真实/占位 SKU、数量、纸单售价和警告确认；
3. 创建正式订单及商品/SKU/价格/成本快照；
4. 建立草稿到正式订单的来源关系；
5. 如有定金，写正式的首笔收款事实，而不是只更新 `paid_amount`；
6. 重算收款快照；
7. 正式订单进入 `CONFIRMED`，履约方式仍为 `UNDECIDED`；
8. 回写草稿 `confirmed_order_id`，重复确认返回同一结果。

确认草稿不能自动选择仓库、创建配货计划或扣库存。人工快速录单直接创建正式订单时，也必须经过同一个正式订单创建服务，避免两套金额和快照逻辑。

#### 13.3.3 保留库存软解耦，但补“业务过账”概念

旧 ERP 的审核同时处理库存、往来和现金，Blade 应改成更清晰的分段事实：

- 正式订单确认：确认销售承诺，建立应收或订单价值事实；
- 收款：建立现金和核销事实，不自动扣库存；
- 选择 `STOCK_LINKED`：允许进入配货，不立即扣库存；
- 发货：唯一销售出库时点；
- `RECORD_ONLY`：不产生库存事实，但仍进入销售和客户分析；
- 作废/退款/退货：分别反向处理订单价值、现金和实物，不能用一个“取消”状态代替。

这样既继承旧 ERP 的账务纪律，又避免“保存一张销售单就同时动所有账”的高风险体验。

#### 13.3.4 已有订单子账与未来通用财务的衔接边界

当前方案中的 `order_financial_record` 适合表达单张订单的收款、核销、退款和冲销，但旧 ERP 实测已经证明生产业务需要：

- 一张收款单核销一张或多张销售单；
- 一张订单被多次收款；
- 一笔钱拆到多个资金账户；
- 超额收款进入预收；
- 预收后续核销新订单；
- 采购侧存在对称的付款、预付和应付核销；
- 账户流水独立于订单生命周期长期存在。

当前 `BE-1041` 与 `order_financial_record` 已完成并通过终审，不再回退。后续新增 `ARCH-FIN-002` 作为通用财务演进门禁，采用：

**通用财务事实为唯一真相。**

- `financial_document`：收款单、付款单、资金调拨、其他收入/支出；
- `financial_document_line`：按一个或多个资金账户拆分实际现金；
- `receivable_payable_entry`：销售应收、采购应付、退货和调整；
- `settlement_allocation`：收付款/预收预付与应收应付的核销关系；
- `financial_event`：追加式收款、付款、优惠、核销、退款、冲销事件；
- 订单和采购单只保存可重算金额快照；
- `order_financial_record` 在 Release A 继续作为订单收款子账；通用财务上线时通过稳定来源 ID 映射为订单级查询投影/兼容子账，禁止双写出两套可独立修改的现金真相。

通用财务实施时应以加法迁移补充 `financial_document_id`、`cash_account_id`、`allocation_id`、`counterparty_type/id` 和冲销引用；迁移前先定义订单子账到通用事实的唯一映射和对账不变量。

### 13.4 商品与订单之间的最终契约

| 场景 | 可选择 SKU | 价格来源 | 库存行为 | 历史保存 |
|---|---|---|---|---|
| 人工快速录单 | 优先真实/默认；显式选择时可占位 | 默认价、客户价或有权限的人工价 | 不检查或仅软提示 | 商品、SKU、规格、价格、成本快照 |
| Agent 草稿 | 可未匹配、占位或真实 SKU | 纸单价为候选成交价，系统价用于差异提示 | 无 | 原始文本、候选、警告、确认结果 |
| 草稿确认 | 未匹配禁止；占位可进入正式订单 | 人工确认后的纸单价 | 无 | 来源关系、确认人、快照 |
| 采购单 | 仅真实/默认 SKU | 供应商约定价或人工采购价 | 审核/确认入库后增加库存 | 供应商货号、单位、采购价、SKU 快照 |
| 配货 | 仅真实/默认 SKU | 不改变订单成交价 | 保存计划和软提示 | 计划 SKU、仓库、数量及调整原因 |
| 发货 | 仅真实/默认 SKU | 使用订单快照 | 唯一销售扣库存时点 | 实际 SKU、仓库、成本和流水 |
| 退货 | 必须对应真实退回 SKU | 使用原单快照或批准调整 | 验收入库时增加库存 | 原销售明细、退回 SKU、金额和原因 |

## 14. 建议的任务编排

### 14.1 编排原则

1. 不把“完整 ERP 替换”一次性塞进当前订单大重构 release。
2. 当前 `ORDER-SOW-0`～`ORDER-SOW-10` 继续作为订单核心主线，但在 SOW-1 前插入财务模型门禁。
3. 商品 v2 已完成的界面和素材能力不重做，只补领域边界和主数据。
4. 采购、应付和通用资金账建立在稳定的订单状态/财务契约之后，作为下一阶段独立工作流。
5. 每个工作包必须有数据库不变量、租户/权限、幂等、回滚和跨模块对账验收，不能只以页面完成为准。

| 15 | `ORDER-SOW-7/8` + `ERP-E2E-001` | 历史迁移、全链路回归、release 和 NAS 准备 | CR-3～CR-6、ERP P0 闭环 | 生产副本迁移、T01-T10 等价测试、恢复演练和四账不变量通过 |

### 14.3 推荐的三个发布阶段

#### Release A：稳定近期商品与订单基础

范围：V43-V50 的既有能力、占位 SKU 拆分保护、订单新状态/财务事实、草稿交接、PC/移动端兼容、统计消费者和历史订单迁移。

目标：商品、草稿、正式订单、收款和库存履约的边界稳定。此阶段不强行上线完整采购和应付，以免当前订单大重构无限扩围。

发布门槛：`ORDER-SOW-0`～`ORDER-SOW-8` 对应门禁通过；V42 生产副本可连续迁移；占位 SKU 永不扣库存；逐笔收款可追溯；旧客户端兼容。

#### Release B：库存接替与价格隐私

范围：供应商最小主数据、供应商—商品关系、无金额也可过账的采购入库、盘点、盘盈亏、其他出入库、四仓库存、工厂角色价格隔离、旧单只读档案，以及销售单/常用标签打印。

目标：先接替旧 ERP 的真实用途——多规格、多仓库存管理。工厂人员能够处理数量和库存，但任何页面或数据出口都不能泄露采购价、销售价、订单金额和利润；未定价使用明确状态，不使用 0 伪装。

发布门槛：期初库存快照与旧 ERP 四仓逐 SKU 对平；盘点差异和盘盈亏来源可追溯；库存流水可重算结存；价格隐私全出口测试通过；旧历史单可按单号、SKU、仓库、日期和制单人只读查询。

#### Release C：新财务真相、经营报表与高级能力

范围：资金账户、收付款、AR/AP、核销、采购/销售金额补录、退货退款、四账对账和经营报表；批次、串码、发票等仅按新业务需求逐项启用。

目标：在库存接替稳定后，从切换日开始建立旧 ERP 从未可靠承载的真实价格、成本、应收应付、现金和利润体系。

发布门槛：库存、应收、应付和资金分别可由事实流水重算；财务报表只统计已定价/已对账事实；冲销不删除原事实；跨租户、权限、缓存和并发测试通过。

## 15. ERP-GAP-001 结论与任务调整（2026-09-03）

真实使用度审计已完成，原始数量和样例见[旧 ERP 功能审计第 11 节](./legacy-erp-functional-audit.md)。业务方进一步确认，旧 ERP 后期主要作为库存系统使用：由于工厂人员无法被可靠屏蔽出厂价和销售价，商品价格和业务单金额被主动录为 0。因此库存数量链仍有价值，但旧金额、应收应付、结算状态、成本和毛利不能直接作为财务真相。

1. 确认价格开始被置零的大致时间边界，并登记真实金额所在的外部账本；567 张零金额进货单不得解释为免费采购；
2. 315 个空单位商品的默认映射与人工例外；
3. 销售/进货各 8 张未审核单的处置结果；

5. 销售主表与开票工作列表之间的未开票差异；
6. 盘点单、盘盈亏单、库存流水和期末结存的来源对账。

`ERP-DATA-001` 未通过时，不允许把旧 ERP 的金额、成本或“未处理”状态直接写入生产新模型。

### 15.3 新系统必须解决的价格隐私缺陷

旧 ERP 失败的不是“有没有隐藏价格按钮”，而是工厂人员在完成库存工作时仍能接触不应看到的价格数据，最终迫使企业牺牲金额真实性。Blade 必须把价格隐私作为后端数据边界：

- 工厂角色默认只看商品标识、颜色尺码、仓库、数量和库存动作；不得获得出厂价/采购价、销售价、订单金额、AR/AP、资金账户、成本、毛利。
- 采购价、销售价、订单金额、成本与毛利分别授权，不用一个“财务权限”粗粒度全开。
- 列表、详情、搜索、联想、API、导出、打印、分享、Agent 数据包和缓存都执行同一字段裁剪；不能只在 Vue 页面隐藏列。
- 无权字段应从响应中移除或返回明确受限状态，绝不能用 `0` 伪装，否则真实零价与权限遮罩无法区分。
- 工厂人员仍可创建和处理库存业务单，价格由有权限人员维护或由受控价格规则自动带入；库存过账不能要求工厂人员看到金额。
- 自动化测试必须使用工厂账号直接访问接口、构造导出/打印请求并验证缓存隔离，防止通过 URL、接口响应或共享缓存绕过前端。

这组要求并入 `ARCH-PROD-001`、`ARCH-FIN-002` 和价格隐私增量任务，并由 `TEST-ERP-PRICE-PRIVACY-001` 单独验收。

### 16.2 三条核心工作流

#### 工厂采购入库

```text
工厂人员录 SKU/属性/数量/仓库
        ↓
提交入库（看不到采购价）
        ↓
库存审核后生成入库流水
        ↓
有权限人员可另行补采购价/供应商账款
        ↓
财务确认后 valuation_status 由 UNPRICED → PRICED/RECONCILED
```

库存入库不能因价格未知而失败；价格未知也不能自动写 0、自动标记已付款或形成虚假毛利。

#### 销售与仓库履约

```text
办公室创建有价格的销售订单
        ↓
仓库只收到 SKU/颜色/尺码/数量/仓库/备注的配货任务
        ↓
实际发货生成销售出库流水
        ↓
订单金额、收款和利润只对授权角色可见
```

仓库不能通过订单详情 URL、搜索接口、打印、导出或 Agent 数据包反查价格。

#### 盘点与盘盈亏

```text
创建盘点范围并冻结账面快照
        ↓
录入实盘数 → 自动计算差异
        ↓
复核人确认
        ↓
差异分别生成盘盈/盘亏调整流水
        ↓
盘点单、调整单、库存流水可双向追溯
```

### 16.3 迁移策略：期初快照与历史档案分离

不建议把旧 ERP 的 2,144 张销售单、873 张进货单和数千张盘点/调整单重放到 Blade 活跃库存账。重放容易重复影响结存，也会把无效金额带入财务模型。建议：

1. 清洗并迁移商品、真实 SKU、颜色尺码、单位、客户、供应商、四个仓库和职员映射。
2. 在停写时点按真实 SKU×仓库导入期初库存，生成唯一 `MIGRATION_OPENING` 库存事件。
3. 旧销售、进货、盘点、盘盈亏和其他出入库进入独立只读档案，不参与新库存和财务重算。
4. 档案保留旧单号、日期、SKU/属性、仓库、数量、方向、制单人和原始备注；金额字段标记 `LEGACY_UNTRUSTED`。
5. 新系统从切换时点开始形成可信库存流水；财务只从已定价或外部账本对账确认的事实开始。
6. 切换验收以“四仓逐 SKU 结存一致”为首要门槛，而不是历史金额合计一致。

新增 `ERP-ARCHIVE-001` 承担旧单只读档案，避免为了保留查询能力而污染新系统的活跃业务表。

### 16.4 明确不做

- 不复制旧 ERP 的视觉样式、组合状态和保存即自动处理全部账务。
- 不把无权查看的价格返回为 0。
- 不把旧单“已付款”当真实结清证据。
- 不重放历史单据来构造期初库存。
- 不在当前 V2 夹带批次、串码、保质期、套餐、组装、积分或完整发票平台。
- 不让报表自行从商品当前价格反推历史利润。
