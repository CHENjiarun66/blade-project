# 如何设计订单金额、结清与经营统计

> 内容类型：概念设计与统计口径。更新时间：2026-08-29。

> 实现状态：业务口径已确认，数据库、接口、界面和统计查询尚未按本文实施。订单生命周期以 [14-ORDER_LIFECYCLE_REFACTOR_DESIGN.md](./14-ORDER_LIFECYCLE_REFACTOR_DESIGN.md) 为准。

本文定义订单金额、实际收款、退款、短款核销、尾款和经营统计之间的关系。它解决“客户少付但业务确认结清”以及状态重构后统计范围变化的问题。

## 一、金额设计的核心原则

金额模型必须区分业务价值和现金流。订单金额回答“卖了多少”，收款流水回答“收到多少”，短款核销回答“放弃收多少”，库存流水回答“实际发出多少”。

本次设计遵循以下原则：

- “已结清”不等于“客户已足额付款”
- 客户实收、现金退款和短款核销分别记录
- 尾款由服务端根据金额快照计算
- 前端不能直接提交最终收款状态
- 订单统计、现金统计、结清统计和库存统计使用不同时间字段
- `RECORD_ONLY` 和 `STOCK_LINKED` 都可形成销售，只有后者影响库存
- 草稿不进入正式财务和经营统计

## 二、如何理解有差额但已结清

差额是否继续追收，决定订单是部分收款还是已结清：

| 订单金额 | 实际收款 | 差额 | 业务决定 | 收款状态 |
|---:|---:|---:|---|---|
| 404.00 | 400.00 | 4.00 | 继续追收 | `PARTIAL` |
| 404.00 | 400.00 | 4.00 | 确认不再追收 | `SETTLED` |
| 400.00 | 400.00 | 0.00 | 足额收款 | `SETTLED` |

第二种情况不再称为“仍有尾款未付”。系统把 4 元记为短款核销，尾款变成 0，但客户实收仍是 400 元。

界面统一使用“已结清”，不使用“已付全款”。订单履约状态也不再使用“已付款”。

## 三、订单金额分层

金额字段分为订单价值、现金和结清调整三组。

### 3.1 订单价值

| 指标 | 字段建议 | 说明 |
|---|---|---|
| 订单原始金额 | `total_amount` | 商品销售金额加运费收入 |
| 销售退回金额 | `sales_return_amount` | 退货或批准的销售减少 |
| 调整后订单额 | `adjusted_order_amount` | 原始金额减销售退回 |

计算规则：

```text
adjusted_order_amount =
max(total_amount - sales_return_amount, 0)
```

`sales_return_amount` 表示销售价值减少，不表示已经向客户退现金。

### 3.2 现金收付

| 指标 | 字段建议 | 说明 |
|---|---|---|
| 累计实收 | `gross_received_amount` | 所有有效 `RECEIPT` 流水合计 |
| 累计现金退款 | `cash_refund_amount` | 所有有效 `REFUND` 流水合计 |
| 净实收 | `net_received_amount` | 累计实收减现金退款 |

计算规则：

```text
net_received_amount =
max(gross_received_amount - cash_refund_amount, 0)
```

### 3.3 结清调整

| 指标 | 字段建议 | 说明 |
|---|---|---|
| 短款核销 | `write_off_amount` | 明确不再追收的金额 |
| 当前尾款 | `balance_amount` | 仍需向客户收取的金额 |
| 多收金额 | `overpayment_amount` | 净实收超过结清要求的金额 |

计算规则：

```text
settlement_required_amount =
max(adjusted_order_amount - write_off_amount, 0)

balance_amount =
max(settlement_required_amount - net_received_amount, 0)

overpayment_amount =
max(net_received_amount - settlement_required_amount, 0)
```

系统默认禁止新增会形成多收金额的收款。历史迁移或特殊业务出现多收时，系统标记异常，不能静默吞掉差额。

## 四、收款状态和结清方式

### 4.1 收款状态

收款状态由当前金额快照计算：

| 条件 | 状态 | 文案 |
|---|---|---|
| `balance_amount > 0` 且 `net_received_amount = 0` | `UNPAID` | 未收款 |
| `balance_amount > 0` 且 `net_received_amount > 0` | `PARTIAL` | 部分收款 |
| `balance_amount = 0` 且不存在未处理多收异常 | `SETTLED` | 已结清 |

零金额订单必须经过人工确认才能进入 `SETTLED`，避免错误金额自动结清。

### 4.2 结清方式

结清方式用于解释订单为什么达到 `SETTLED`，不增加新的收款状态：

| 值 | 说明 |
|---|---|
| `FULL_RECEIPT` | 净实收达到调整后订单额 |
| `WRITE_OFF` | 净实收加短款核销达到调整后订单额 |
| `MIGRATION_CONFIRMED` | 历史数据迁移时确认已结清 |

系统根据财务流水计算结清方式。前端不直接写该字段。

### 4.3 短款核销限制

短款核销必须满足：

- 订单存在正数实收，不能把整张未收款订单直接核销为已结清
- 核销金额不能超过当前尾款
- 核销原因必填
- 记录操作人、操作时间和来源
- 超过配置金额或比例时要求更高权限
- 已结清订单不能重复核销

## 五、财务流水与金额快照

### 5.1 财务流水表

新增 `order_financial_record`，统一记录会改变订单财务结果的动作：

| 字段 | 说明 |
|---|---|
| `order_id` | 正式订单标识 |
| `record_type` | 财务动作类型 |
| `amount` | 本次金额，必须大于 0 |
| `payment_method` | 现金、转账等方式，可空 |
| `occurred_at` | 业务发生时间 |
| `operator_id` | 操作人 |
| `reason` | 核销、退款或冲销原因 |
| `source` | PC、移动端、Agent、迁移等来源 |
| `idempotency_key` | 外部请求幂等键 |
| `reversed_record_id` | 被冲销的原流水，可空 |
| `tenant_id` | 租户标识 |

`record_type` 第一版包含：

| 类型 | 影响 |
|---|---|
| `RECEIPT` | 增加累计实收 |
| `WRITE_OFF` | 增加短款核销 |
| `REFUND` | 增加现金退款 |
| `REVERSAL` | 冲销指定流水，不删除原记录 |
| `MIGRATION_OPENING` | 写入无法还原逐笔历史的期初金额 |

流水只追加，不直接修改或物理删除。错误流水通过 `REVERSAL` 冲销。

### 5.2 订单金额快照

`sale_order` 保留以下快照，供列表、筛选和报表查询：

- `gross_received_amount`
- `cash_refund_amount`
- `net_received_amount`
- `write_off_amount`
- `balance_amount`
- `collection_status`
- `settlement_method`
- `settled_at`

统一财务快照服务根据有效流水重算这些字段。业务服务、Controller 和前端不能分别维护公式。

### 5.3 旧字段兼容

现有 `payment_status`、`paid_amount`、`refund_amount`、`deposit_amount` 和 `pay_time` 在兼容期保留：

- `payment_status` 只保存 `collection_status` 的 `0/1/2` 兼容投影，不再作为新业务判断依据
- `paid_amount` 暂时映射累计实收，但不再作为流水真相
- `deposit_amount` 保留首笔部分收款历史快照
- `pay_time` 保留旧接口兼容，新增 `settled_at` 表达结清时间
- `refund_amount` 当前同时包含销售减少和现金退款语义，不能直接迁移成两个新字段

旧退款数据必须结合退货单、库存流水和现金记录判断。缺少证据时进入人工核对清单。

## 六、订单详情的金额展示

金额区域同时展示订单价值、现金和结清调整。以订单 404 元、实收 400 元、核销 4 元为例：

| 项目 | 展示值 |
|---|---:|
| 订单金额 | 404.00 |
| 销售退回 | 0.00 |
| 客户实收 | 400.00 |
| 已退款 | 0.00 |
| 净实收 | 400.00 |
| 短款核销 | 4.00 |
| 待收尾款 | 0.00 |
| 收款状态 | 已结清 |
| 结清方式 | 短款结清 |

下方按时间展示财务流水：

```text
08-20 收款 200.00
08-25 收款 200.00
08-29 短款核销 4.00，原因：客户少付尾款
```

界面把“已付金额”统一改为“客户实收”或“累计实收”。核销金额不能合并进客户实收。

## 七、统计指标分组

状态重构后，系统不再使用一个订单查询同时计算所有指标。

### 7.1 订单指标

订单指标回答正式订单的规模和欠款结构：

| 指标 | 统计范围 | 时间字段 |
|---|---|---|
| 正式订单数 | 非草稿、非取消订单 | `order_date` |
| 订单原始金额 | 正式订单 `total_amount` | `order_date` |
| 未收款订单额 | `collection_status=UNPAID` | `order_date` |
| 部分收款订单额 | `collection_status=PARTIAL` | `order_date` |
| 已结清订单额 | `collection_status=SETTLED` | `order_date` |
| 当前应收余额 | 所有非取消订单的 `balance_amount` | 当前快照 |

取消订单不进入经营订单额，但其历史收款、退款和冲销仍保留在现金流统计中。

### 7.2 销售指标

销售指标区分订单承诺和已经结清的成交结果：

```text
net_sales_amount =
adjusted_order_amount - write_off_amount
```

| 指标 | 统计范围 |
|---|---|
| 订单额 | 所有非取消正式订单，不要求已收款 |
| 已结清销售额 | `collection_status=SETTLED` 的净销售额 |
| 待结清订单额 | `UNPAID` 和 `PARTIAL` 的调整后订单额 |
| 短款核销额 | `WRITE_OFF` 流水 |
| 核销率 | 短款核销额除以调整后订单额 |

销售分析默认按 `order_date` 归属业务月份。订单后续结清时，历史业务月份的“已结清销售额”可能回补。系统另按 `settled_at` 展示本期结清效率，不能把两类指标合并。

### 7.3 现金流指标

现金流只根据财务流水的 `occurred_at` 统计：

| 指标 | 计算 |
|---|---|
| 本期实收 | `RECEIPT + MIGRATION_OPENING` |
| 本期现金退款 | `REFUND` |
| 本期净收款 | 实收减现金退款和相关冲销 |
| 本期核销 | `WRITE_OFF` |
| 收款笔数 | 有效 `RECEIPT` 流水数 |

订单创建于 8 月 1 日、尾款收于 8 月 20 日时，订单额归属 8 月 1 日，现金实收归属 8 月 20 日。

### 7.4 履约与库存指标

库存统计只使用实际库存动作：

| 指标 | 统计范围 | 时间字段 |
|---|---|---|
| 待配货订单 | `STOCK_LINKED` 且处于待配货或配货中 | 当前快照 |
| 实际出库量 | 已完成的出库流水 | 出库发生时间 |
| 仓库发货额 | 实际出库明细对应销售额 | 出库发生时间 |
| 库存周转 | 实际出库数量和库存快照 | 出库发生时间 |

`RECORD_ONLY` 订单不进入库存周转、仓库发货和实际出库统计。

### 7.5 商品与规格指标

商品分析保留两套销量：

- **订单销量**：非取消正式订单明细，反映已确认需求
- **已结清销量**：已结清订单明细，反映成交结果

`PLACEHOLDER` 数量计入款号总销量，但不进入真实颜色、尺码和可出库 SKU 排名。`STOCK_LINKED` 订单拆分后必须转移数量，不能同时保留占位和真实 SKU 数量。

## 八、统计范围矩阵

| 订单类型或状态 | 订单额 | 已结清销售额 | 实收现金 | 商品销量 | 库存出库 |
|---|---|---|---|---|---|
| 草稿 | 否 | 否 | 否 | 否 | 否 |
| 正式未收款 | 是 | 否 | 否 | 是 | 否 |
| 正式部分收款 | 是 | 否 | 按流水 | 是 | 否 |
| 已结清 `RECORD_ONLY` | 是 | 是 | 按流水 | 是 | 否 |
| 已结清 `STOCK_LINKED` 未发货 | 是 | 是 | 按流水 | 是 | 否 |
| 已发货 `STOCK_LINKED` | 是 | 是 | 按流水 | 是 | 是 |
| 已取消 | 否 | 否 | 历史流水保留 | 否 | 仅保留已发生流水 |

“商品销量”默认显示订单销量时，界面必须标注统计口径。库存相关页面只能使用实际出库数量。

## 九、毛利统计

短款核销直接减少收入和毛利。退货还可能冲回商品成本，因此不能继续使用“原毛利减退款金额”的简化公式。

建议公式：

```text
net_revenue =
total_amount - sales_return_amount - write_off_amount

net_cost =
total_cost_amount - returned_cost_reversal_amount

net_gross_profit =
net_revenue - net_cost
```

退回商品重新入库时，系统记录 `returned_cost_reversal_amount`。商品损坏或未回库时，不冲回对应成本。完整退货模块实施前，报表必须标注当前毛利退款口径限制。

## 十、状态变化对现有统计的影响

现有查询必须清理以下模式：

- 使用 `status >= 4` 判断已发货或已完成
- 使用 `status=0` 统计全部待处理订单
- 使用“已付款”订单状态判断是否产生销售
- 仅凭 `paid_amount > 0` 判断订单是否进入全部分析
- 使用订单日期统计实际收款和退款
- 把 `RECORD_ONLY` 订单计入库存周转

改造后使用明确枚举、履约方式、财务流水和对应业务时间。取消、退货和核销不能通过数字范围比较推断。

## 十一、旧数据迁移与核对

财务迁移先生成只读审计报告：

- 汇总订单金额、累计实收、退款、核销和尾款
- 查找实收为负、退款为负、超收和整单核销
- 查找收款状态与金额公式不一致的订单
- 查找已结清但仍有正数尾款的订单
- 查找部分收款但尾款为 0 的订单
- 查找退款存在但缺少退货或现金证据的订单
- 查找订单日期、收款时间和结清时间缺失的订单

无法恢复逐笔历史时，迁移写入 `MIGRATION_OPENING`，并保留来源说明。迁移不能伪造具体收款日期、方式和操作人。

迁移完成后核对以下不变量：

- 订单总数不变
- 订单原始金额汇总不变
- 已知累计实收汇总不变
- 已知退款与核销汇总不变
- 每张订单的新尾款能由快照公式复算
- 财务迁移不创建库存流水

## 十二、实施顺序

金额和统计必须与订单状态重构联动实施：

1. 新增财务流水表和金额快照字段
2. 建立统一快照计算服务
3. 改造草稿确认、正常收款、短款核销、退款和冲销
4. 改造订单详情金额区与财务流水
5. 按订单、销售、现金、履约和库存拆分统计查询
6. 改造仪表盘、分析、客户、导出和 Agent 数据接口
7. 在生产数据副本上执行迁移预演和金额对账
8. 生产备份后迁移，并核对金额与库存不变量

金额模型、状态机和统计查询不能分三个版本独立切换。过渡期接口同时返回旧字段和新快照，所有写入仍由新财务服务统一处理。
