## 一、项目概述

### 1.1 项目背景

BladeProject 是对原有 Blade 项目的重大技术升级，采用 **Monorepo 结构**，包含：
- **blade-backend**：Spring Boot 3 后端 API
- **blade-mobile**：Vue3 PWA 移动端（员工操作）
- **blade-admin**：Vue3 PC 端后台管理系统（管理后台）
- **packages/**：共享代码（API 类型定义）

### 1.2 技术栈

| 层级 | 技术 |
|------|------|
| 移动端 | Vue3 + Vite + TypeScript + PWA + Vuetify 4 |
| PC 管理端 | Vue3 + Vite + TypeScript + Element Plus |
| 后端 | Spring Boot 3.2 + Spring Security + MyBatis-Plus |
| 数据库 | MySQL 8 + Redis 7 |
| AI 工具 | Codex（当前主力） |

### 1.3 前端项目定位

| 项目 | 定位 | 使用场景 | 技术栈 |
|------|------|----------|--------|
| blade-mobile | 移动端 PWA | 员工移动操作：接单、扫码出入库、订单查询 | Vue3 + Vuetify 4 + PWA |
| blade-admin | PC 管理端 | 管理员：订单管理、库存管理、商品管理、客户管理、报表 | Vue3 + Element Plus |

**设计原则**：
- 两个前端项目独立开发，通过共享 `packages/` 中的 API 类型保持一致性
- blade-mobile 专注移动端体验（触屏、扫码、简洁）
- blade-admin 专注 PC 端体验（表格、批量操作、复杂筛选）

### 4.8 商品管理 v2：SKU 精细维护与商品素材管理

当前商品模块第一版已满足商品建档、颜色/尺码选择、SKU 自动生成、商品主图上传和基础 CRUD。v2 的目标是让商品资料维护能直接支撑生产录单、iPad 现货展示和后续数据分析，不再要求管理员频繁跳转到文件中心才能完成商品素材维护。

#### 4.8.1 商品编辑页结构

PC 商品编辑页应从单一表单升级为分区或 Tab 式编辑：

| 区域 | 目标 |
|------|------|
| 基础信息 | 商品编码、名称、分类、单位、进货价、批发价、重量、状态、描述、备注 |
| 颜色尺码 | 选择商品启用的颜色和尺码，继续自动生成/同步 SKU |
| SKU 明细 | 按颜色/尺码展示 SKU 列表，可逐行维护售价、成本价、条码、状态和 SKU 图片 |
| 商品素材 | 维护商品主图、商品图集；可从本地上传，也可从文件中心选择已有文件 |

第一版可以保留弹窗编辑形态，但必须避免 SKU 明细和图片素材挤在同一个长表单里；若弹窗承载过重，应改为商品详情/编辑页。

#### 4.8.2 SKU 明细维护规则

SKU 由商品 + 颜色 + 尺码生成，商品编码不允许在编辑时修改。SKU 明细维护必须满足：

- 颜色/尺码组合新增时，创建新的正常状态 SKU。
- 颜色/尺码组合移除时，不物理删除已有 SKU；优先软删除或禁用，避免影响历史订单和库存引用。
- 已存在 SKU 的 `price`、`cost_price`、`bar_code`、`status` 可单独编辑。
- 更新商品级进货价/批发价时，不应强制覆盖已手动维护过的 SKU 价格；如确需批量同步，应提供显式按钮或二次确认。
- 快速录单、订单编辑和 Catalog 只展示正常状态 SKU；历史订单继续显示订单明细快照，不依赖商品/SKU 当前名称。
- SKU 行应展示颜色名称、尺码、SKU 编码、售价、成本价、条码、状态、SKU 图片数量或缩略图。

#### 4.8.3 商品素材规则

商品素材统一走文件中心和 `file_business_bind` 绑定关系，不新增商品图集或 SKU 图片业务字段。

| 素材类型 | 绑定规则 |
|----------|----------|
| 商品主图 | 同步 `product.image_url` 保存原始 fileId，并写入 `file_business_bind` 的 `businessType=product, bindRole=main` |
| 商品图集 | 写入 `businessType=product, bindRole=gallery`，按 sort 排序 |
| SKU 图片 | 写入 `businessType=sku, bindRole=sku_image`，SKU 表不直接保存图片字段 |

商品编辑页应支持：

- 上传并设置商品主图。
- 上传/选择多张商品图集图片，支持排序、移除、预览。
- 在 SKU 明细行中绑定 SKU 图片，支持查看缩略图和移除。
- 历史 URL 或历史 fileId 继续兼容展示。
- 图片预览仍通过统一 `filePreviewUrl(fileId)` 或后续 `fileVariantUrl(fileId, type)`，不得手写裸 `/api/files/{id}/preview`。

#### 4.8.4 图片性能规则

商品列表、商品编辑页缩略图、文件中心网格、订单图片墙和 Catalog 卡片后续应优先加载派生图：

- 列表/卡片场景优先使用 `card`。
- 小缩略图、胶片条、SKU 行缩略图优先使用 `thumb`。
- 点击预览、大图、下载仍使用原图。
- 派生图缺失时必须兜底原图，不影响页面使用。

派生图底座对应任务为 `BE-1012`；PC 接入对应 `BA-1007`；Catalog 接入对应 `BA-1028`。

#### 4.8.5 删除与历史引用规则

- 商品、SKU、颜色、尺码、分类均应以软删除或禁用为主，避免破坏订单、库存、文件绑定和 Catalog 历史引用。
- 删除商品前应校验是否存在订单明细、库存记录或有效文件绑定；存在有效引用时，默认不允许删除，建议改为禁用。
- 若仅无业务引用，允许软删除，并同步处理有效 SKU 状态。
- 商品删除/禁用不得删除文件中心真实文件，只能解绑或保留绑定关系。

#### 4.8.6 供应商边界

供应商表和 `product.supplier_id` 已在 PRD 中预留，但供应商管理仍不是商品 v2 第一优先级。商品 v2 第一版只保留 supplierId 字段兼容，不开发供应商 CRUD；供应商模块应在商品录入、SKU 图片和派生图性能稳定后单独规划。

### 5.5 库存操作规则

1. **订单创建**：不扣库存，只记录意向
2. **订单收款/确认收款**：只更新订单收款状态和履约优先级，不检查库存、不锁定库存，不得因库存不足失败
3. **订单配货**：查看库存、选择实际发货 SKU/仓库/数量；库存不足、缺库存记录、替换 SKU 均只做提示和记录，不阻断配货方案保存
4. **订单发货**：按实际发货明细出库，扣减 `quantity`；这是订单流程中唯一真实扣减销售库存的节点
5. **直接调整**：记录调整原因，可正可负

**双轨预留规则**：
- `reserved_qty`：单仓预占场景使用
- `global_reserved_qty`：历史跨仓总量预留字段，第一版生产订单流程暂停使用；后续若基于超卖率重新启用，只能作为软预留/优先级能力，不得阻断录单和收款

### 6.2.1 PC 快速录单与财务快照

- 快速录单用于把纸质订单按单张连续录入系统，最终仍保存到 `sale_order` / `sale_order_item` 标准订单表。
- 快速录单页面按 PC 后台高频录入场景布局：单据/客户信息在上方，商品明细居中，结算与配送和金额汇总在商品明细下方左右并列展示，减少录入时上下滚动和视线跳转。
- 快速录单新增“按商品批量录入 SKU”作为第一优先操作路径：录单员先搜索/选择商品款号或商品名称，再在该商品的 SKU 矩阵中直接填写各颜色/尺码数量，点击“添加到订单”后一次性生成多条订单明细。
- 批量 SKU 矩阵第一版只展示正常状态 SKU，不读取、不展示、不校验库存数量；库存为 0、未建库存记录或库存模块数据不完整时，均不得影响订单录入。快速录单与库存流程暂时解耦，后续库存提醒只能作为非阻塞提示另行设计。
- 批量添加时，数量为空或 0 的 SKU 不写入订单明细；数量大于 0 的 SKU 写入现有 `items` 明细结构。若相同 `skuId` 已存在于当前订单明细中，自动合并数量，不新增重复行，且不覆盖原明细中已手动修改过的单价和成本价。
- 保留现有明细表作为已添加商品的复核与修正区，支持继续修改数量、单价、成本价和删除行；原单 SKU 搜索添加能力可作为备用路径保留，但不应成为高频录入主路径。
- “来源档口/店铺”用于记录订单来自哪个档口商店，是订单来源字段；不绑定库存仓库，也不参与库存预留、出库逻辑。
- 订单类型仅作标记与筛选：`SPOT` 现货订单，`PREORDER` 订货订单；第一版不改变库存提醒和发货流程。
- 运费分两项：`freight_amount` 为向客户收取的运费，计入订单应收；`freight_cost` 为实际运费成本，计入订单成本。
- 利润公式：`gross_profit = 商品销售小计 - 商品成本金额 + 运费收入 - 运费成本`。
- 成本价、成本金额和毛利在订单保存时固化为历史快照，后续商品成本变化不影响历史订单。
- 后续追加收款只更新 `paid_amount`、`payment_status` 和必要的抹零/短款结清字段，不自动改变订单处理状态。

### 6.3 订单状态流转（处理进度）

> 订单状态描述发货/履约进度，支付状态描述收款情况。两个状态互相独立：收款变化不得自动跳过配货、发货、完成；库存不足不得阻断录单和收款。完整设计和流程图见 `06-ORDER_INVENTORY_DESIGN.md` 与 `architecture/order-inventory-soft-coupling-flow.drawio`。

**当前实现状态模型（9 状态）**：

```text
创建(0) → 已付款(1) → 配货中待确认(2) → 待发货(3) → 已发货(4) → 已完成(5)
      └──────────────────────────────→ 已取消(6)
已发货(4) → 退货中(7) → 已退货(8)
```

| 状态码 | 名称 | 库存操作 |
|--------|------|---------|
| 0 | 创建 | 无 |
| 1 | 已付款/待配货 | 无；标记为已产生收款订单，进入优先配货队列 |
| 2 | 配货中待确认 | 无；只记录实际配货/替换/减配方案 |
| 3 | 待发货 | 无；已完成配货确认，等待实际发货 |
| 4 | 已发货 | 按实际发货明细扣减库存 |
| 5 | 已完成 | 无 |
| 6 | 已取消 | 无；若已有收款按退款流程处理，不自动改库存 |
| 7 | 退货中 | 无 |
| 8 | 已退货 | 退货入库 |

**状态流转规则**：
- 创建(0) → 已付款(1)：确认收款时
- 已付款(1) → 配货中待确认(2)：创建配货计划后
- 配货中待确认(2) → 待发货(3)：确认调整方案后
- 待发货(3) → 已发货(4)：仓库按配货计划发货
- 已发货(4) → 已完成(5)：订单完成
- 创建(0) / 已付款(1) / 配货中待确认(2) → 已取消(6)：人工取消
- 已发货(4) → 退货中(7) → 已退货(8)：退货流程

**与旧版差异**：原设计 `payment_status=2(已付全款)` 时自动设置 `status=1`，现已改为手动确认收款操作。

### 6.4 收款状态

与订单状态是两个独立维度：

| 收款状态码 | 名称 | 说明 |
|------------|------|------|
| 0 | 未付款 | 客户未付款或仅登记未收款 |
| 1 | 部分收款 | 客户已付部分金额，仍需继续收尾款 |
| 2 | 已结清 | 客户已付清，或少量差额已通过抹零/短款结清确认不再追收 |

**与订单状态的关系**：
- 订单状态描述"处理进度"，支付状态描述"收款情况"
- `payment_status=2(已结清)` 时，**手动确认收款**后设置 `status=1(已付款/待配货)`
- `payment_status=0(未付款)` 的订单仍可取消，不涉及退款

**结清口径**：
- 应收净额：`receivable_net_amount = max(total_amount - refund_amount - write_off_amount, 0)`。
- 尾款：`balance_amount = max(receivable_net_amount - paid_amount, 0)`。
- `payment_status=0`：`paid_amount = 0`。
- `payment_status=1`：`0 < paid_amount < receivable_net_amount`，表示部分收款/待收尾款。
- `payment_status=2`：`paid_amount >= receivable_net_amount`，表示已结清。
- 例：订单应收 312，客户实付 310，确认不再追收 2 元时，记录 `write_off_amount=2`，应收净额为 310，收款状态为已结清。

**抹零/短款结清规则**：
- 用于客户实际少付但业务确认不再收尾款的场景，不应继续显示为“部分收款”。
- 抹零金额应计入销售额和毛利扣减，避免经营数据虚高。
- 抹零/短款结清不得自动改变发货状态，只影响收款状态、尾款展示和统计口径。
- 追加收款弹窗支持“标记结清”：自动将当前尾款写入 `write_off_amount`，并将 `payment_status` 更新为 2；结清原因必填。

**确认收款操作**：
- 接口：`POST /api/orders/confirm-payment`
- 参数：`orderId`, `paidAmount`
- 效果：更新 `paid_amount`、`payment_status`、`pay_time`；订单处理状态 0→1，进入待配货/优先配货队列；不检查库存、不调用跨仓预留、不因库存不足失败

### 6.4.1 订单编辑权限规则

订单编辑按状态分级，避免已收款订单金额被误改，同时保留纸质单图片等非金额资料维护能力：

| 订单状态 | 可修改内容 | 锁定内容 |
|----------|------------|----------|
| 创建(0) | 客户信息、订单类型、日期、纸质单号、来源档口、配送、备注、订单图片、运费、商品明细、成本价 | 无 |
| 已付款/待配货(1) | 客户信息、订单类型、日期、纸质单号、来源档口、配送、备注、订单图片 | 商品明细、数量、单价、成本价、运费收入、运费成本、应收、成本、毛利、收款金额 |
| 配货中(2) / 待发货(3) | 客户信息、配送、备注、订单图片；配货相关调整应走配货计划 | 商品明细、数量、单价、成本价、运费、金额结构 |
| 已发货(4) 及以后 | 备注、订单图片；退款/退货走独立流程 | 客户核心信息、商品明细、数量、单价、成本价、运费、金额结构 |

**实现要求**：
- 前端应在编辑弹窗中禁用不可修改字段，避免用户误以为保存会生效。
- 后端必须兜底校验：已收款订单不得修改金额结构；已发货后仅接收备注和订单图片。
- 订单图片属于纸质单据/凭证资料，不参与金额结构，已付款后仍应允许追加、移除和重新绑定。

### 6.6 订单与库存联动

**软解耦流程**（生产优先口径）：

> 详细设计见 `06-ORDER_INVENTORY_DESIGN.md`

```
1. 订单创建（status=0）
   → 不绑定仓库（支持先下单、后配仓）
   → 不扣库存，不预占，不检查库存

2. 确认收款（status=0 → 1）
   → 变更 paid_amount、payment_status、pay_time
   → 订单进入待配货/优先配货队列
   → 不调用 global_reserve，不锁定 global_reserved_qty
   → 库存不足只能提示，不得阻断收款确认或追加收款

3. 配货确认（status=1 → 2 → 3）
   → 创建配货计划，进入配货中待确认
   → 仓库查看当前库存，记录实际发货 SKU、仓库、数量
   → 支持替换 SKU、减配、备注说明和后续退款/补发
   → 确认后进入待发货

4. 订单发货（status=3 → 4）
   → 按实际发货明细出库
   → 扣减 quantity
   → 第一版不要求扣减 global_reserved_qty
   → 记录库存变动日志

5. 订单取消（status=6）
   → 未发货订单可取消
   → 已收款订单需单独走退款记录
   → 不自动释放 global_reserved_qty

6. 退货入库
   → 增加可用库存（quantity + quantity）
   → 记录库存变动日志
```

**关键设计**：
- **订单优先**：订单是业务事实，库存是履约能力；录单和收款必须稳定可用
- **库存软提示**：库存不足、无库存记录、替换 SKU 只提示和记录，不阻断订单主流程
- **发货扣减**：只有实际发货会扣减销售库存
- **历史字段兼容**：`global_reserved_qty` 和 `inventory_global_reserve` 暂不删除，避免生产迁移风险；第一版生产订单流程不依赖它们

| `/api/agent/analytics/sku-mix` | GET | 款式颜色/尺码/SKU 结构事实 |
| `/api/agent/tasks/follow-up` | GET | 需跟进客户清单与提醒依据 |
| `/api/agent/customers/risk` | GET | 客户流失风险与分层事实 |
| `/api/agent/inventory/recommendations` | GET | 库存积压、缺货和补货优先级事实 |
| `/api/agent/reports/periodic` | GET | 月度、季度、年度经营分析数据包 |
| `/api/agent/search` | GET | 客户、订单、商品/SKU 跨模块搜索 |

实现时优先复用 `/api/dashboard/*`、`/api/analytics/*` 和客户统计能力，统计口径不得与现有看板、数据分析页分叉。

### 10.3 安全与权限

1. Agent 使用独立凭证，不复用前端 JWT 登录态。
2. 每个 Agent 凭证必须绑定 `tenant_id` 和 scope，认证通过后进入当前多租户隔离链路。
3. 第一版 Agent API 默认只读，禁止创建/编辑订单、库存调整、收款确认等高风险动作。
4. 成本、毛利、毛利率需单独授权，默认不返回。
5. 对外开放 Agent 前必须复核客户数据接口认证边界、Agent API 调用审计和限流。

### 10.4 暂缓范围

- 后端自然语言问答 `/agent/query` 暂缓，先由外部 Agent 调用结构化工具接口。
- 泛化写动作 `/agent/action` 暂缓；后续只允许经过明确授权的窄范围动作。
- 增量变化接口 `/agent/changes` 依赖统一业务事件日志，第一版不纳入验收。
- WhatsApp 的 Agent 分析和自动营销不纳入当前验收；本地归档 v1 先实现只读采集、结构化事实、客户映射和导入审计。
- 订单流程异常、利润解释、WhatsApp 反馈分析和经营记忆属于后续能力路线，按事件、权限和外部数据接入成熟度分阶段落地。

## 十二、OCR 拍照录单（P2）

> 优先级 P2，等订单核心流程跑通后再重点开发。
> 目标：尽量减少手动输入，让入单流程尽可能简单。

### 9.1 核心目标

**拍照 → 自动识别 → 自动填表 → 一键确认**

理想情况：完全不用手动选，识别完直接提交。

### 9.2 字段识别难度分析

| 字段 | 识别难度 | 原因 | 预估准确率 |
|------|---------|------|-----------|
| 款号 | 🔴 最难 | 非标准缩写、无固定格式、手写潦草、AI 无法猜对应关系 | 40-60% |
| 客户名称 | 🔴 难 | 手写中文、字迹潦草、可能有别名/简称 | 60-70% |
| 日期 | 🟡 中等 | 格式多样（2024.1.15 / 2024年1月15日 / 24.1.15） | 85%+ |
| 单价 | 🟡 中等 | 手写数字为主，但有¥符号辅助定位 | 80%+ |
| 数量 | 🟢 较易 | 纯数字、结构清晰、在表格内 | 90%+ |
| 总金额 | 🟢 最易 | 经常预印或在固定位置、有"¥"符号辅助 | 90%+ |

**核心结论**：款号识别是最大难点，必须有兜底方案。

### 9.3 字段识别策略

| 字段 | 处理策略 | 原因 |
|------|---------|------|
| 数量 | ✅ 自动填入 | 识别准确率高 |
| 单价 | ✅ 自动填入 | 有¥符号定位，准确率高 |
| 总金额 | ✅ 自动填入 | 位置固定，准确率高 |
| 客户名称 | ✅ 自动填入 | 识别后自动填，可修改 |
| 日期 | ✅ 自动填入 | 数字为主，自动填 |
| **款号** | ⚠️ **手动选择** | 识别难，预设不填，用户从商品库选择 |

### 9.4 实施方案

#### 方案 A：半自动录单（推荐，P2 优先实现）

**核心思路**：款号识别不准确 → 预设不填；数量/单价/总金额识别准确 → 自动填入。

**流程**：
```
拍照 → OCR 识别 → 数量/单价/总金额/客户名/日期自动填入 → 用户只选款号 → 提交
```

**表单设计**：
```
┌─────────────────────────────────────────────────────────────┐
│  📷 拍照录单 - 单据识别结果                                   │
├─────────────────────────────────────────────────────────────┤
│  客户：张三（自动填入，可修改）  📅 2024-01-15              │
│                                                              │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ # │ 款号（手动选择）     │ 颜色  │ 数量 │ 单价 │ 小计 │  │
│  ├───────────────────────────────────────────────────────┤  │
│  │ 1 │ [从商品库选择 ▼]    │ 黑色  │  10  │ ¥120 │ ¥1200│  │
│  │ 2 │ [从商品库选择 ▼]    │ 白色  │   5  │ ¥135 │ ¥675  │  │
│  └───────────────────────────────────────────────────────┘  │
│                                                              │
│  总额：¥ 1875（自动计算）  已付：□定金 ¥500  □全款          │
│  送货：☑ 需要送货  地址：[________________]                    │
│                                                              │
│                    [ 确认提交订单 ]                            │
└─────────────────────────────────────────────────────────────┘
```

**工作量对比**：
| 方案 | 操作步骤 |
|------|---------|
| 原来（无 OCR） | 选款号 → 选颜色 → 填数量 → 填单价 → 选仓库 → 填客户 → ... |
| 方案 A（半自动） | 拍照 → 选款号 → 提交（减少 80% 操作） |

**优点**：
- 款号跳过识别，只靠人工选，避免识别错误
- 数量/单价是最高频字段，自动填入节省大量时间
- 逻辑简单，不依赖 AI 模糊匹配
- 容错率高，款号选错了可以改

#### 方案 B：AI 辅助全自动化（后续探索）

**核心思路**：OCR + AI 智能匹配商品库 + 置信度标注 + 用户确认。

**流程**：
```
拍照 → OCR 识别 → AI 解析结构 → 模糊匹配商品库 → 生成预填表单 → 用户核对修正 → 提交
```

**AI 解析示例**：

输入（OCR 识别后的文字）：
```
客户：张三  138xxxx
日期：2024-01-15

款号        颜色    数量    单价
001         黑      10      120
002         白      5       135
```

输出（AI 解析后）：
```json
{
  "customerName": "张三",
  "customerPhone": "138xxxx",
  "items": [
    {
      "skuCode": "P001-BLACK-M",
      "productName": "经典T恤",
      "colorName": "黑色",
      "quantity": 10,
      "price": 120,
      "confidence": "high"
    },
    {
      "skuCode": "P002-WHITE-M",
      "productName": "休闲裤",
      "colorName": "白色",
      "quantity": 5,
      "price": 135,
      "confidence": "medium"
    }
  ]
}
```

**置信度标注**：
| 置信度 | 表现 | 处理 |
|--------|------|------|
| 高 | 绿色标识，自动填入 | 直接使用 |
| 中 | 橙色标识，填入但待确认 | 用户确认/修改 |
| 低 | 红色标识，预设为空 | 用户手动选择 |

**界面设计**：
```
┌─────────────────────────────────────────────────────────────┐
│  📷 拍照录单 - AI 智能识别                                   │
├─────────────────────────────────────────────────────────────┤
│  📋 识别结果预览（绿色=高置信 橙色=待确认 红色=需手动）        │
├─────────────────────────────────────────────────────────────┤
│  客户：张三  138xxxx                           ✅ 高置信      │
│                                                              │
│  商品明细：                                                  │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ 001 经典T恤   黑色   x10   ¥120    ✅ 高置信          │  │
│  │ 002 休闲裤    白色   x5    ¥135    ⚠️ 中置信(待确认) │  │
│  └──────────────────────────────────────────────────────┘  │
│                                                              │
│  款号识别候选（如置信度低）：                                  │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ 002 可能匹配：                                        │  │
│  │   - P002-白色-M（经典衬衫）← 推荐                     │  │
│  │   - P005-白色-S（休闲T恤）                           │  │
│  └──────────────────────────────────────────────────────┘  │
│                                                              │
│  ⚠️ 2 个商品需要您确认                                       │
│                                                              │
│                    [ 确认提交订单 ]                            │
└─────────────────────────────────────────────────────────────┘
```

**技术要点**：
- AI 模糊匹配款号（支持缩写、谐音、部分匹配）
- 颜色名称标准化映射（"黑" → "黑色"，"BLK" → "黑色"）
- 置信度评分机制
- 逐步学习优化（用户修正记录用于模型改进）

#### 方案 C：纯手动录单（基线方案）

无 OCR，直接手动输入所有字段。

### 9.5 技术方案

| 模块 | 方案 | 说明 |
|------|------|------|
| OCR 服务 | 微信扫一扫 / 腾讯云 OCR | 手写识别效果好 |
| AI 解析（方案B） | 本地 LLM 或云函数 | 解析文字结构，提取字段 |
| 商品匹配（方案B） | 模糊匹配算法 | 支持缩写、模糊搜索 |
| 图片存储 | 统一文件入口 + fileId 保存 | 第一版本地存储，后续可切七牛云/NAS；详见 [09-FILE_STORAGE_DESIGN.md](./09-FILE_STORAGE_DESIGN.md) |

### 9.6 实施计划

**Phase 1：基础版（方案 A，半自动）**
1. 统一图片上传接口（复用文件存储模块）
2. OCR 识别文字服务
3. 表单字段提取（数量/单价/总金额/客户名/日期）

**Phase 2：AI 增强版（方案 B，全自动）**

5. 用户快速确认/修正

### 9.7 OCR 识别准确率保证

| 措施 | 说明 |
|------|------|
| 保留人工确认环节 | 不强制自动填充，识别结果仅供参考 |
| 置信度标注 | 高亮标注"不确定"字段，提醒用户检查 |
| 修正记录 | 用户修正历史用于优化识别模型 |
| 逐步学习 | 越用越准 |

## 十三、文件中心与客户展示页（P1）

> 详细设计见：[12-FILE_CENTER_ASSET_DESIGN.md](./12-FILE_CENTER_ASSET_DESIGN.md)

### 13.1 产品定位

文件中心不是单纯图片/视频相册，而是系统统一的数字资产中心。

第一版重点服务三个场景：

1. 后台统一管理所有上传图片和基础视频文件。
2. 管理未绑定到商品、SKU、订单或入库记录的临时文件，支持定期清理。
3. 为客户 iPad 现货展示页提供商品/SKU 图片来源。

### 13.2 核心规则

| 规则 | 说明 |
|------|------|
| 业务表继续保存 fileId | 禁止业务表保存物理路径 |
| 文件资产独立管理 | 图片、视频、后续文档均进入文件中心 |
| 业务关系走绑定表 | 商品、SKU、订单、入库日志关系统一走 `file_business_bind` |
| 商品主图兼容旧字段 | `product.image_url` 继续保存主图 fileId，同时同步绑定关系 |
| 未绑定文件可治理 | 未绑定、未归档、超过保留期的临时文件可自动软删除 |
| 私有文件需鉴权 | 订单图片、入库凭证、OCR 原图默认私有 |
| 列表优先加载派生图 | 商品列表、订单图片墙、文件中心网格、Catalog 卡片等列表/卡片场景应优先加载缩略图或中图，点击大图/下载时再加载原图 |

### 13.3 文件中心能力边界

第一版必须支持：

- PC 后台 `/files` 文件中心。
- 文件夹管理。
- 图片上传、预览、移动、软删除。
- 基础视频文件上传和基础预览。
- 未绑定文件筛选和清理。
- 绑定到商品主图、商品图集和 SKU 图片。
- 查看并追加绑定订单图片、入库凭证。

第一版不做：

- 视频转码。
- 分片上传和断点续传。
- 七牛云/NAS 切换。
- 客户公开分享链接。
- AI 自动打标签。
- 文档在线预览。
- 文件版本管理。

后续性能优化必须支持：

- 图片上传后生成派生图版本，至少预留 `thumb` 和 `card` 两种用途。
- 业务表仍只保存原始 `fileId`，不得保存缩略图路径或派生图路径。
- 派生图权限继承原图权限，私有文件的缩略图也必须经过统一鉴权。
- 历史图片允许后续批量补生成；派生图缺失时可兜底原图，避免页面不可用。
- 当前系统规模仍小时，派生图第一版应先打好架构脚手架：统一派生图服务、统一存储 Provider、统一 URL 工具、可表达状态的派生图表结构，避免后续接 NAS、七牛云、CDN 或异步队列时重构业务表和页面调用链。
- 脚手架只保留扩展点，不提前实现复杂外部能力；第一版仍以本地存储、`thumb/card`、同步或轻量异步生成、失败可回退原图为边界。
- 视频封面、转码、分片上传仍作为后续独立能力，不纳入图片派生图第一版。

### 13.4 客户 iPad 展示页

新增只读客户展示页，建议路由：

```text
/catalog
```

或：

```text
/showroom
```

页面用于 iPad 展示现货服装，数据来自系统商品、SKU、文件中心图片绑定和实时库存。

第一版展示规则：

| 能力 | 说明 |
|------|------|

## 十八、架构决策记录

### 14.1 软删除机制（2026-03-22）

**决策**：系统所有数据实行软删除，禁止物理删除。

**原因**：
1. 数据可追溯，满足财务审计要求
2. 历史订单、库存记录等核心数据永不丢失
3. 避免数据关联断裂导致的统计异常

**规则**：
- 所有业务表必须有 `deleted` 字段（tinyint，默认 0）
- 删除操作必须使用 `UPDATE SET deleted = 1`，禁止 DELETE
- 查询时自动过滤 `deleted = 1` 的数据
- 特殊情况下可查询已删除数据用于数据恢复

**实现**：
- MyBatis-Plus 配置 `LogicDeleteInterceptor` 自动处理
- 配置 ignore-tables 排除不需要软删的表（如系统配置表）

### 14.2 订单冗余字段（2026-03-22）

**决策**：订单明细表保留商品名称、颜色、尺码等冗余字段。

**原因**：
1. 订单是财务核心数据，必须保证任何时候都能完整展示
2. 查询性能优化，避免多表 JOIN
3. 历史追溯：客户对账时需要看到下单时的商品信息

**规则**：
- 商品表（product）实行软删除，禁止物理删除
- 订单创建时填充冗余字段
- 冗余字段作为"快照"，极端情况下保证可展示性

### 14.4 OCR 拍照录单（2026-03-23）

**决策**：订单系统支持 OCR 拍照录单，实现半自动/全自动识别填表。

**优先级**：P2，等订单核心流程跑通后再重点开发。

**原因**：
1. 批发业务录单频繁，手动输入效率低
2. 款号识别是最大难点，必须有兜底方案
3. 用户核心诉求：尽量把手写或手动填入做到最低

**方案选择**：
- **Phase 1（推荐）**：方案 A 半自动 - 款号手动选，其他自动填入
- **Phase 2（后续）**：方案 B AI 全自动 - OCR + AI 模糊匹配 + 置信度标注

**核心原则**：
- 保留人工确认环节，不强制自动填充
- 款号识别不准 → 预设不填，用户手动选择
- 数量/单价识别准 → 自动填入

**决策**：订单系统支持"部分收款/尾款/已结清/抹零短款"和"送货状态"两个核心线下流程。

**原因**：
1. 批发业务常见先付定金、后付尾款的分期付款方式
2. 送货状态是线下录单的重要环节，与订单处理进度独立
3. 灵活的资金处理是线下记账的核心痛点
4. 少量短款但业务确认不再追收的场景应视为已结清，不应长期显示欠款

**规则**：
- 收款状态（payment_status）：0未付款 / 1部分收款 / 2已结清
- 定金金额（deposit_amount）：作为初始部分收款金额快照使用，历史兼容保留
- 抹零/短款结清（write_off_amount）：客户少付但确认不再追收时使用，计入销售额和毛利扣减
- 送货设置（need_delivery, delivery_address, is_delivered）：与订单状态独立
- 收款状态=已结清时，仍需按订单处理状态正常配货/发货/完成，不自动跳过履约流程
- 收款状态=未付款时，订单仍可取消

### 14.5 外部 AI Agent 对接（2026-05-22）

**决策**：新增只读 Agent Gateway，外部 Agent 通过受控 API 获取款式趋势、客户跟进清单、周期经营报告数据包、搜索和分析结果。

**原因**：
1. 当前系统已经有看板、数据分析、库存预警和沉默客户等聚合能力，适合作为 Agent 数据底座。
2. 直接向 Agent 暴露数据库会绕开多租户、业务口径和权限约束。
3. Agent 写操作风险高，必须先验证只读接入、凭证和审计边界。

**规则**：
- Agent 使用独立凭证并绑定租户与 scope。
- 第一版不实现后端自然语言问答和泛化写动作。
- Agent 统计优先复用现有领域服务，避免与看板/分析口径漂移。
- WhatsApp 信息属于后续客户沟通上下文扩展，需先验证合规接入、客户映射和消息权限，再进入实现。
- 统一业务事件日志落地后，再评估 `/api/agent/changes` 和窄范围授权动作。

### 14.6 WhatsApp Mac 本地归档（2026-08-24）

**决策**：先以当前 WhatsApp Business Mac App 为只读数据源，建立 Git 外原始归档和 Blade 内结构化事实层；继续使用原号码，不接自动回复。

**原因**：
1. 当前本机数据已验证可只读提取，能满足先集中存档和分析的目标。
2. WhatsApp 私有 SQLite 可能变化，需要用快照、schema guard、源行映射和幂等重放隔离风险。
3. 聊天信息是沟通上下文，不应覆盖 ERP 客户、订单和人工标签等业务真相。

**规则**：
- 原始数据库和媒体只读，快照/真实内容不得进入 Git。
- v1 只接 1:1 联系人、会话、消息和已下载媒体；群聊、状态、发送能力后置。
- 不自动创建 CRM 客户；只有唯一精确号码可以产生待确认绑定候选。
- Collector 使用独立导入凭证，Agent 只通过 scoped Gateway 读取必要事实。
- Agent 只生成偏好与跟进建议，不自动执行营销。
