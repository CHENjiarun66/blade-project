### [2026-05-22] 需求 #006 - 外部 AI Agent 对接

**提出者**：用户

**需求描述**：
- 希望 BladeProject 对接 AI Agent，参考外部 Agent 架构设计稿筛选可复用方案。
- Agent 重点帮助判断款式趋势：哪些款持续向好，哪些款不建议继续做。
- Agent 需要基于客户订单和日期定时提醒需要跟进的客户。
- 后续希望接入 WhatsApp 信息，让 Agent 结合聊天上下文与系统数据分析客户状态。
- 需要支持月度、季度、年度经营分析和建议。
- 用户认可继续扩展 Agent 能力，未想到的经营场景由 AI 帮助补充规划。

**AI 分析**：
- 当前系统已经具备看板、经营分析、库存预警、客户订单日期和沉默客户等“答案型”能力，可作为 Agent Gateway 的底座。
- BladeProject 已锁定 MySQL、Redis、多租户、SKU + 仓库库存、订单配货与权限模型，不能直接照搬参考文档的数据库表和接口草案。
- Agent 接入要先守住租户隔离、数据权限和审计边界，第一期不应开放泛化写操作或后端自然语言查询。
- 除用户已提出方向外，Agent 还适合规划颜色尺码结构、库存取舍、客户流失风险、订单异常、利润解释、沟通反馈、异常检测和经营记忆等能力。

**方案建议**：
- 新增只读 Agent Gateway v1，第一期提供款式趋势、颜色尺码结构、客户跟进/风险、库存建议事实、周期经营报告数据包和跨模块搜索。
- Agent 使用独立凭证，绑定租户与 scope，毛利/成本数据需单独授权。
- WhatsApp 接入先作为第二阶段方案验证，先锁定合规接入、客户映射、权限、保留和脱敏策略。
- 订单运营异常、利润解释、WhatsApp 反馈分析、经营记忆等能力写入后续路线，按事件日志、毛利权限和外部数据接入成熟度排序。
- 后续在统一业务事件日志基础上再扩展变更订阅和窄范围 Agent 写动作。

**结果**：✅ 采纳

### [2026-08-24] 需求 #007 - WhatsApp Mac 本地归档与 ERP/Agent 集成

**提出者**：用户

**需求描述**：
- 继续使用当前 WhatsApp Business 号码和 Mac App，不换号码。
- 先把联系人、聊天文本和已下载媒体统一归档到本地电脑，不需要自动回复。
- 把结构化聊天事实与 Blade ERP 的客户、订单、商品和库存结合。
- 后续由 Agent 分析客户偏好、营销时机和需要跟进的客户，但营销动作由用户决定。
- 建表前先形成详细计划，锁定边界、表字段、开发内容和各 Agent 分工，再开始开发。

**AI 分析**：
- 当前 Mac App 的 ChatStorage、Contacts、Labels 和 Biz SQLite 可只读访问，但属于 WhatsApp 私有结构，必须通过一致性快照、schema guard 和版本化适配降低升级风险。
- 消息源行存在逻辑重复，旧行还会在媒体下载后更新；不能只按最大主键增量，需逻辑消息键、源行引用和内容哈希三层幂等。
- 原始归档与 ERP 结构化事实应分层：原始快照留在 Git 外的加密本地目录，Blade MySQL 只保存业务所需记录和媒体引用。
- WhatsApp 联系人不能批量自动创建 ERP 客户；只做租户内规范化号码精确匹配候选，并保留人工确认。
- Agent 继续走只读 Gateway，不直连源库/MySQL，不自动发消息或覆盖人工标签。

**方案建议**：
- 采用“Mac 只读快照 → 独立 Collector → Blade 内部导入 API → `wa_*` 事实表/文件中心 → Agent Gateway”的链路。
- v1 先实现 1:1 联系人、会话、文本、已下载媒体、CRM 绑定和导入审计；群聊、状态、自动发送、推荐模型和 Business Platform 后置。
- 详细字段、唯一键、SOW、测试矩阵和分工以 `docs/superpowers/plans/2026-08-24-whatsapp-local-archive-rom-sow.md` 为实施契约。

**结果**：✅ 采纳

**同步到 PRD**：已同步到 `02-PRD.md` WhatsApp 本地归档 v1、`03-TASKS.md` BE-564/BE-566～BE-571 和 `10-AGENT_INTEGRATION_DESIGN.md`

### [2026-08-24] 需求 #008 - WhatsApp 媒体同步完整性工作台

**提出者**：用户

**需求描述**：
- Mac WhatsApp 有时只同步消息，图片或视频尚未下载。
- 需要一个采集分析表，列出未正常加载的聊天和媒体。
- 用户打开对应 WhatsApp 聊天加载图片/视频后，再运行脚本补齐数据。

**AI 分析**：
- 可可靠检测 Mac 已有消息或媒体元数据但本地路径为空、文件不存在、仅有缩略图、大小不一致或导入失败。

**方案建议**：
- 新增 `wa_collection_issue` 保存稳定问题键、缺失类型、状态、重复次数和发现/恢复时间。
- 工作台按客户/联系人、媒体类型、问题类型和状态筛选，提供打开聊天和重新扫描入口。
- 用户补下载后，Collector 通过旧源行 `Z_OPT/row_hash` 和实际文件 hash 识别补齐，复用原逻辑消息并把问题转为 `RESOLVED`。

### [2026-08-24] 需求 #009 - WhatsApp 本地预处理、NAS 集中分析与 Agent 推荐

**提出者**：用户

**需求描述**：
- WhatsApp 原始数据先在 Mac 本地安全提取和整理，再同步到 NAS 上的 Blade ERP。
- 可以在本地先由确定性 Engine 做解析、去重和完整性检查；NAS 结合 ERP 数据做长期分析。
- 用户不参与脚本运行，只在 ERP 查看客户画像、商品偏好和跟进建议。

**AI 分析**：
- 全部在 Mac 分析会受关机、换机和 ERP 数据割裂影响；原始数据直接上传公有云又会扩大隐私、成本和供应商风险。
- 最稳妥的是混合架构：Mac 作为安全采集边缘，NAS 作为结构化事实和 Agent 中心，云端模型仅接收脱敏、限时、最小化上下文。
- Agent 输出必须包含证据消息 ID、置信度和模型版本；只能生成建议，不能自动发消息、覆盖人工标签或修改订单。

**方案建议**：
- Mac：只读快照、schema guard、标准化、哈希、媒体完整性和幂等上传。
- NAS：客户绑定、聊天时间线、订单/商品事实、分析队列、画像与跟进推荐。
- 云端/本地模型：通过可替换 Agent Worker 消费最小上下文并返回固定 JSON；原始 SQLite、完整电话、姓名、地址和媒体默认不出 NAS。

**结果**：✅ 采纳

**同步到 PRD**：已同步到 `02-PRD.md`、`10-AGENT_INTEGRATION_DESIGN.md`、混合 Agent ROM/SOW 和 `03-TASKS.md` BE-571/BE-573～BE-576、BA-1102
