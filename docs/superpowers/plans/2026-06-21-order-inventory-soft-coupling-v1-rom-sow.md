# ROM/SOW: 订单与库存软解耦生产版 v1

> 日期：2026-06-21  
> 分支：`feature/order-inventory-soft-coupling-v1`  
> 任务：`BE-124`、`BE-126`、`BE-138`、`BE-139`、`BE-140`、`BE-142`、`BA-212`、`BA-213`、`TEST-ORDER-INV-001`  
> 协作方式：Claude Code 负责受限范围实现，Codex 负责方案锁定、逐轮 Diff 审查、独立测试和最终验收。

## 一、目标

完成可用于生产环境的订单与库存软解耦第一版：

1. 创建订单、确认收款、追加收款、取消订单和确认减配均不锁定、预留或释放库存。
2. 配货计划允许在库存不足时保存，库存只作为软提示。
3. 只有确认发货时，才按实际配货 SKU、仓库和数量校验并扣减库存。
4. 统一当前两条发货路径，避免状态错乱、重复扣减和不同接口采用不同库存规则。
5. 支持抹零/短款结清，并统一尾款、销售额、毛利、筛选和导出口径。
6. 建立覆盖收款、配货、发货、结清、租户隔离、幂等和事务回滚的自动化测试基线。

## 二、本轮明确排除

以下能力本轮不分析、不修复、不顺带重构：

- 部分发货、分批发货、拆包发货。
- 缺货退款、缺货自动退金额、按 SKU 分摊退款。
- 采购、补货、到货、订货库存流程。
- 自动选择仓库或智能配货推荐。
- 删除 `inventory_global_reserve` 表或 `global_reserved_qty` 字段。
- 重写库存模块、订单状态机或出库单模块的无关能力。
- 生产数据库操作、NAS 发布和历史库存数据修复。

如果实现中发现上述能力阻塞当前任务，必须停止扩展并向 Codex 报告，不得自行扩大范围。

## 三、已核实的当前问题

### 3.1 收款仍硬依赖库存

`OrderServiceImpl.confirmPayment()` 当前调用 `reserveInventoryGlobal()`，导致库存不足时无法确认收款，与生产口径冲突。

### 3.2 配货减配仍释放库存预留

`OrderDeliveryPlanServiceImpl.confirmAdjustment()` 当前调用 `globalReleasePartial()`。收款阶段取消预留后，这条逻辑会释放不存在的预留。

`OrderServiceImpl.updateStatus()` 在目标状态为取消时还会调用旧的 `releaseInventory()`，虽然当前控制器没有直接暴露该入口，但它仍属于订单状态服务的库存副作用，必须同步移除或收紧。

### 3.3 按计划出库仍依赖全局预留

`InventoryServiceImpl.outByPlan()` 当前要求 `global_reserved_qty >= quantity`，并在出库时扣减 `global_reserved_qty`，不符合“发货时直接校验实际库存”的新口径。

### 3.4 存在两条发货路径

- `OrderServiceImpl.deliverOrder()` 通过配货计划调用 `outByPlan()`。
- `OrderDeliveryServiceImpl.confirmDelivery()` 直接调用 `inventoryService.out()`，并包含旧订单状态值判断和更新。

两条路径可能产生状态不一致或双重扣减风险。

### 3.5 抹零结清尚未实现

`write_off_amount`、`write_off_reason` 尚无 migration、实体、DTO、接口和前端交互；尾款、欠款筛选、导出、仪表盘和分析统计仍按旧公式计算。

## 四、锁定业务规则

### 4.1 收款与库存独立

- 创建订单不查询、不校验、不修改库存。
- 确认收款和追加收款不查询、不校验、不修改库存。
- 取消未发货订单不释放库存，因为订单流程不再创建硬预留。
- 确认减配不释放库存。
- 收款状态变化不得自动跳过配货、发货或完成状态。

### 4.2 配货为计划，不是库存占用

- 配货计划记录计划 SKU、仓库和数量，但不改变库存。
- 配货时可读取库存用于提示，库存不足不得阻止保存方案。
- 本轮不做自动替换 SKU；备注和调整记录用于描述人工替换/减配结果。

### 4.3 发货才扣库存

- 只有确认发货动作可以扣减订单对应库存。
- 扣减依据是已确认配货计划中的实际 SKU、仓库和待出库数量。
- 第一版校验可用量为 `quantity - reserved_qty`，订单发货不依赖 `global_reserved_qty`。
- 库存不足必须返回包含 SKU、仓库、可用量和需求量的业务错误。
- 一次整单发货涉及多条计划时必须保持事务原子性：任意一条失败，全部库存、计划状态和订单状态回滚。
- 同一订单、配货计划或出库单重复确认不能重复扣库存。
- 两个发货入口并发调用时必须先按订单串行化，或使用带状态条件的数据库原子更新取得唯一执行权；仅依赖库存行乐观锁和方法开头读取订单状态不视为完整幂等。

### 4.4 发货路径统一

- 对外已有接口暂不删除，避免破坏现有前端和历史调用。
- 所有确认发货入口必须委托同一个底层事务服务或共享领域方法。
- 禁止一条路径调用 `outByPlan()`、另一条路径直接执行不同库存规则。
- 订单状态统一使用当前 `0-8` 定义，不允许继续使用“status=2 表示已发货”的旧逻辑。
- 本轮只保证现有整单发货闭环，不新增部分发货语义。

### 4.5 抹零/短款结清

- `payment_status=0`：未付款。
- `payment_status=1`：部分收款。
- `payment_status=2`：已结清，不再限定为实收全款。
- 新增 `write_off_amount`，默认 0；`write_off_reason` 可空。
- 应收净额：`max(total_amount - refund_amount - write_off_amount, 0)`。
- 尾款：`max(total_amount - refund_amount - write_off_amount - paid_amount, 0)`。
- 销售额和毛利统计扣减 `write_off_amount`。
- 标记结清时，将当前尾款写入 `write_off_amount`，必须填写或保留明确原因。

### 4.6 数据与兼容边界

- Flyway 只能新增 migration，不修改已执行的 V1-V38。
- 保留历史全局预留表和字段，不做破坏性 migration。
- 新代码不得为订单创建新的全局预留记录。
- 旧数据若已有全局预留，本轮不自动清理；另行建立受控数据治理任务。
- 所有订单、配货计划、出库、库存查询和写入必须保持租户隔离。

### SOW-1：测试先行与收款去预留 `BE-138`

范围：

- 为确认收款、追加收款、取消订单、确认减配增加新口径测试。
- 移除订单收款、`cancelOrder()`、`updateStatus(..., CANCELLED)` 和减配调用全局预留/释放的逻辑。

验收：

- 零库存订单可以确认收款。
- 收款、追加收款、取消和减配前后库存三类数量不变化。
- 现有订单支付状态测试通过。

### SOW-2：发货扣库存与路径统一 `BE-126/BE-139/BE-142`

范围：

- 重构 `outByPlan()`，不依赖 `global_reserved_qty`。
- 建立唯一的底层确认发货事务路径。
- 让现有发货入口复用统一路径，修正旧状态值。
- 增加订单级并发保护，以及库存不足、事务回滚、重复确认、双入口并发和跨租户测试。
- 审计并关闭 `POST /api/inventory/out-by-plan` 绕过订单状态机直接按单条计划扣库的能力；本轮不允许通过该入口形成部分发货。

验收：

- 发货按实际 SKU、仓库和数量扣减 `quantity`。
- 不修改 `global_reserved_qty`。
- 多计划任一失败时全部回滚。
- 两个入口不能造成双重扣减。

### SOW-3：数据库与结清后端 `BE-124/BE-140`

范围：

- 新增下一版本 Flyway migration，增加抹零字段和必要索引。

- 新增或扩展追加收款/标记结清接口。

验收：

### SOW-4：PC 配货软提示 `BA-212`

验收：

### SOW-5：PC 标记结清 `BA-213`

- 少收金额可标记结清，尾款显示 0。
- 已结清订单不再显示追加收款按钮。

## 六、必须覆盖的测试矩阵

| 场景 | 预期 |
|------|------|
