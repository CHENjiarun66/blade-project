## 三、必须联动修改的系统

| 系统 | 当前耦合/问题 | 本次必须完成 |
|------|------|------|
| Flyway / 数据模型 | 旧 `status`、`payment_status` 和金额快照承担多重语义 | 加法迁移、新枚举字段、财务流水、状态日志、并发版本、兼容读取 |
| 订单核心服务 | 多处直接比较或写入数字状态 | 建立统一动作服务和状态机，其他模块不得绕过 |
| 草稿 / Agent 导入 | 草稿确认直接进入旧正式订单模型 | 首笔收款写正式流水；确认后进入 `CONFIRMED`，不自动履约 |
| 收款 / 退款 / 核销 | `paid_amount`、`refund_amount` 无法表达现金与销售退回差异 | 统一财务事实服务、快照重算、冲销而非覆盖历史 |
| 配货 / 出库 / 库存 | 发货入口与旧状态、占位 SKU 强相关 | 仅 `STOCK_LINKED` 可履约；占位未拆分阻断；统一发货事务入口 |
| PC 订单端 | 列表、详情、快捷录单、草稿页硬编码旧状态 | 使用后端动作白名单；展示新状态、流水、尾款和履约选择 |
| 移动端 | 仍是旧四状态模型 | 兼容读取后切换新模型；不得继续提交数字状态 |
| 共享类型 / API | 数字枚举和支付状态被各端复制 | 增加字符串枚举、金额快照、`allowedActions` 和兼容字段 |
| 权限系统 | 只有确认付款和金额字段等粗粒度权限 | 拆分收款、核销、退款、冲销、履约选择、财务查看和迁移权限 |
| 仪表盘 / 分析 | 通过状态范围和 `paid_amount` 自行推断销售 | 改用统一订单/销售/现金/履约事实查询，排除取消和错误状态 |
| 客户系统 | 完成次数和消费额依赖旧状态；缓存可能不失效 | 使用统一统计口径，并在订单/财务/状态变化后失效缓存 |
| Agent / WhatsApp 分析 | `orderFacts` 直接汇总所有未删除订单 | 改用统一事实服务，返回口径版本和数据时间，不自行写 SQL |
| 导出 / Excel | 旧字段无法说明短款结清和净实收 | 增加原始金额、实收、退款、核销、尾款、结清方式和履约字段 |
| 测试 | 大量断言依赖旧数字状态 | 增加状态转移、财务不变量、统计一致性、迁移和兼容测试 |
| NAS 发布 | 生产仅 V42，跨越多个 migration 和功能组 | 必须先在生产副本从 V42 连续预演，再按 release 一次发布完整匹配版本 |

## 四、可以保持边界稳定的系统

以下模块不应借本次机会做无关重构：文件中心底座、WhatsApp 消息采集与媒体归档、商品素材与 Catalog、客户电话和国家区号、普通采购入库、认证基础设施。

它们只需遵守两个接口边界：新产生的订单相关记录必须有租户隔离；需要消费订单数据时只能调用统一事实服务或版本化 API。

## 五、统一架构门禁

1. **单一写入口**：订单状态、财务快照和履约状态只能由领域动作服务修改。
2. **单一事实口径**：仪表盘、分析、客户、Agent、WhatsApp 和导出不得各自重写金额公式。
3. **后端决定动作**：接口返回 `allowedActions`，PC 和移动端只负责展示，不复制状态机判断。
4. **流水不可覆盖**：收款、退款、核销使用追加记录；错误操作通过冲销记录纠正。
5. **旧字段只兼容**：旧 `status` 和支付字段过渡期只做映射，不新增业务语义。
6. **库存后置**：只有 `STOCK_LINKED` 且明细已拆到真实 SKU 才能配货和出库。
7. **生产不可试错**：历史迁移必须先在 V42 生产副本完整预演，输出逐单映射和不变量报告。

目标字段固定为：

| 旧字段 | 新字段 | 兼容规则 |
|------|------|------|
| `status`，整数 | `fulfillment_status`，字符串 | 新状态机写新字段，统一适配器生成旧值 |
| `payment_status`，整数 | `collection_status`，字符串 | 财务快照服务写新字段，统一适配器生成 `0/1/2` |

`fulfillment_mode` 表示库存履约选择，不是第三个替代状态。草稿状态继续存放在独立 `order_draft` 表。本次不新增 `order_lifecycle_status`，避免与 `fulfillment_status` 重复。

## 六、实施工作包与依赖

### SOW-0：只读基线审计

负责人只读扫描代码、SQL、接口和测试，输出准确文件清单、旧状态写入点、金额公式、直接 SQL 消费者和 migration 序列。不得改代码或数据库。

完成条件：扫描结果覆盖订单、库存、统计、客户、Agent、WhatsApp、导出、PC、移动端、共享类型和权限，不再存在未知写入口。

对应 `BE-1040`、`BE-1041`。

- 只新增 Flyway migration，不修改 V1-V50。
- 实体、Mapper、VO 同时支持新旧字段。
- 所有表、索引和查询保持租户隔离。

### SOW-2：订单状态机与财务事实服务

对应 `BE-1042`、`BE-1043`、`BE-1044`。

- 实现确认草稿、收款、短款核销、退款、冲销、选择履约方式、取消和完成动作。

- 旧接口委托新服务，不允许两套写逻辑并存。

## 七、多 Agent 并行规则

建议使用一个集成分支配合独立 worktree/子分支：

```text
feature/order-lifecycle-finance-refactor
├── feature/order-refactor-schema-core
├── feature/order-refactor-fulfillment
├── feature/order-refactor-pc-contracts
└── feature/order-refactor-stats-consumers
```

- 每个 Agent 一次只认领一个 SOW 或任务 ID，并在 `03-TASKS.md` 标记执行人。
- 各 Agent 使用独立 worktree，禁止共享同一个未提交工作区。
- SOW-1 合入集成分支后，SOW-2 才能开始写模型；SOW-2 契约稳定后，SOW-3～SOW-6 才可并行。
- 数据库 migration 版本由一个负责人统一分配，其他 Agent 不得抢号或改已提交 migration。
- 消费者 Agent 不得自行定义状态和金额公式；发现缺字段时回报契约负责人。
- 每次交付必须包含 commit、变更文件、测试命令、测试结果、未决风险和文档同步。
- 未经用户明确确认，任何 Agent 不得 push `master`、合并 release、连接生产执行写操作或发布 NAS。

## 八、Git 与 NAS 策略

本次选择“**先固化当前 Phase 2 基线，再单开重构集成分支**”，不把未完成重构直接上传 NAS。

推荐顺序：

1. 提交并推送本轮设计文档，让 GitHub 分支成为可恢复的交接基线。
2. 先决定 V43-V50 这组累计能力是否作为一个独立 release 完成验收；当前分支同时包含 WhatsApp 和 Phase 2，未验收前不合入 `master`、不部署 NAS。
3. 实现 Agent 使用已从 `5252339` 创建并推送的 `feature/order-lifecycle-finance-refactor`，新 migration 从 V51 以后连续编号。
4. 大重构在该集成分支和独立 worktree 子分支完成，NAS 继续运行 V42 稳定版本。
5. 在 V42 生产副本验证“V42 → V43…V50 → 新迁移”的完整升级路径。
6. 创建 release 并完成自动化、人工和迁移验收。
7. release 合入 `master` 并推送后，按 NAS 日常发布流程备份和部署。

不建议先把当前分支直接部署 NAS 再立刻做大重构，原因是该分支累计包含 V43-V50，WhatsApp 生产接入与纸单 30 单验收均未完成，生产会在短期内经历两轮高耦合 migration 与订单语义切换。只有业务明确需要先使用这组能力，并能将其作为独立稳定版本完整验收时，才单独走一次 release。

## 九、首发不可拆分与可后置范围

首发不可拆分：加法迁移、统一状态机、财务流水和快照、草稿确认、履约方式、占位履约保护、PC 主流程、权限、公共契约、统计事实底座、历史迁移工具。

首发前必须兼容：仪表盘、Analytics、客户统计与缓存、Agent、WhatsApp 订单事实、导出、移动端旧版本读取。

可在稳定后增强：移动端完整新交互、复杂退货/售后、部分发货、财务审批中心、旧兼容字段物理删除。

## 十、验收与停止条件

任何一项不满足都不得发布：

- 不存在绕过状态机直接写状态、付款快照或履约状态的入口。
- 全额收款与短款核销都能结清，但实收和核销始终分开。
- 取消、退款、销售退回和现金退款不会重复冲减。
- `RECORD_ONLY` 永不产生库存流水；占位 SKU 永不直接扣库存。
- 仪表盘、分析、客户、Agent、WhatsApp 和导出对同一筛选范围得到一致事实。
- V42 生产副本升级和迁移可重复预演，异常订单有人工处理清单。
- 跨租户、并发、重复请求和事务回滚测试通过。
- release commit、数据库备份、镜像和回滚入口均可追踪。
- 数据库备份已在隔离库实际恢复，且 NAS 外副本、SHA-256、uploads 清单和不可变前后端镜像齐全。

出现 migration 不可重复、金额不变量不平、库存重复扣减、跨租户访问、统计消费者仍使用旧 SQL、生产备份不可用时，立即停止后续阶段。
