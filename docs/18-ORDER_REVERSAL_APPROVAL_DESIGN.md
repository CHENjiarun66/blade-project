# 订单全流程回退、冲销与审批设计

> 文档状态：设计定稿，尚未开发  
> 形成日期：2026-09-15  
> 适用范围：正式销售订单、收款、履约、配货、出库、完成、取消及后续售后衔接  
> 关联文档：[订单生命周期设计](./14-ORDER_LIFECYCLE_REFACTOR_DESIGN.md)、[订单金额与统计设计](./15-ORDER_FINANCE_ANALYTICS_DESIGN.md)、[旧 ERP 功能审计](./reference/legacy-erp-functional-audit.md)

## 一、结论

系统应支持订单全流程的**受控逆向操作**，但不提供“直接选择任意目标状态”的通用状态编辑器。

每一次逆向操作必须属于以下三类之一：

1. **路径纠错**：尚未产生库存或财务过账事实，只撤销错误选择。
2. **业务撤销**：已经形成配货方案或完成标记，但尚未实际出库，可在依赖校验后撤销确认。
3. **事实冲销**：已经形成库存或财务流水，不能只改状态，必须生成对应反向事实。

状态字段是业务事实的结果，不是用户可以随意编辑的数据。前端只能提交“撤销履约选择”“撤销配货确认”“冲销出库”等明确动作，最终目标状态由后端状态机计算。

## 二、旧 ERP 经验与 Blade 取舍

旧 ERP 的审核与反审核共用 `auditing` 接口，通过动作参数决定方向。T10 实测中，销售单已经关联收款后，系统会阻止直接反审核，并提示先删除收付款单。

Blade 应保留旧 ERP 做对的部分：

- 反向动作必须检查下游依赖。
- 库存、资金、应收和核销有关联时不能只改主表状态。
- 操作必须在事务中完成，失败整体回滚。

Blade 不照搬旧 ERP 的部分：

- 不删除已经发生的收款、库存和调整历史。
- 错误收款使用 `REVERSAL` 冲销，原流水永久保留。
- 错误出库生成反向库存流水，不能删除原出库流水。
- 配货方案取消后保留已取消版本和操作轨迹。
- “回退订单状态”不能代替订单修订、退款、退货或库存冲销。

## 三、状态维度不能混用

订单当前有多个独立状态维度。回退一个维度，不得无理由联动修改其他维度。

| 状态维度 | 主要字段 | 回答的问题 | 回退原则 |
|---|---|---|---|
| 草稿生命周期 | `order_draft.status` | 草稿是否仍可编辑、是否已生成正式订单 | 已生成正式订单后不退回草稿 |
| 收款状态 | `collection_status` | 客户实际收款和核销是否结清 | 由财务流水重算，禁止直接改值 |
| 履约方式 | `fulfillment_mode` | 是否关联库存 | 尚未产生库存事实时可以撤销选择 |
| 履约状态 | `fulfillment_status` | 配货、发货、完成走到哪里 | 未过账可撤销；已过账必须冲销 |
| 配货计划状态 | 配货计划状态及版本 | 当前配货方案是否有效 | 取消或替换，不物理删除历史 |
| 售后状态 | 后续独立字段 | 是否退货、换货或退款 | 不塞回履约状态，本阶段预留 |

特别说明：

- `need_delivery` 只表示是否需要物流送货，不代表是否关联库存。
- “已确认”仍是正式订单，不是草稿，也不代表可以任意修改商品和金额。
- 履约回退不自动撤销收款。订单从待配货退回已确认后，仍可保持“已结清”。
- 商品、数量、售价填写错误属于“订单修订”，不是单纯状态回退。

## 四、回退风险与审批等级

### 4.1 四级处理方式

| 等级 | 名称 | 是否需要另一账号审批 | 适用范围 |
|---|---|---:|---|
| R0 | 二次确认后直接执行 | 否 | 无配货计划、无库存/财务副作用的路径纠错 |
| R1 | 负责人审批 | 通常需要 | 已形成方案或完成标记，但尚未实际库存过账 |
| R2 | 职责分离审批 | 必须，申请人与审批人不能相同 | 库存冲销、结清财务冲销等已形成业务事实的逆向操作 |
| R3 | 禁止直接回退 | 不进入普通审批 | 已取消订单恢复、正式订单退回草稿、跨结账期强制改状态等 |

“二次确认”和“审批”不是一回事：

- 二次确认是在同一次操作中再次展示影响，原操作人确认后立即执行。
- 审批是先形成待审批申请，由有审批权限的另一账号批准后才执行。

### 4.2 Owner 自助例外

R1 动作可以提供租户级“Owner 强验证自助执行”开关。启用后，`ROLE_OWNER` 可通过重新验证登录身份、填写原因并再次确认后执行，不必等待另一账号。

R2 动作默认禁止自批：

- 申请人和审批人必须是不同用户 ID。
- 库存冲销由仓库人员申请、Owner 审批。
- 财务冲销由财务人员申请、Owner 审批。
- 小团队如果只有一个业务账号，应先创建独立审批账号，不能用共享账号绕过职责分离。

## 五、完整状态回退矩阵

### 5.1 草稿与正式订单边界

| 当前状态 | 是否可回退 | 正确操作 | 条件 | 审批 |
|---|---:|---|---|---|
| 草稿 `EDITING` | 不称为回退 | 继续编辑或作废草稿 | 尚未确认 | 作废需二次确认，R0 |
| 草稿 `CONFIRMED` | 否 | 到正式订单处理；需要重录时复制为新草稿 | 已经生成正式订单 | R3，禁止恢复为可编辑草稿 |
| 草稿 `VOID` | 否 | 新建或复制草稿 | 已作废 | R3 |
| 正式订单 `CONFIRMED` | 不退回草稿 | 订单修订、取消订单或选择履约方式 | 根据财务和依赖决定可用动作 | 见对应动作 |

正式订单一旦生成，原草稿的 `CONFIRMED` 记录只用于幂等、防重和审计。不得恢复草稿后再次确认，否则可能产生重复正式订单和重复财务流水。

### 5.2 收款状态

收款状态只能通过不可变财务流水计算，不提供“把已结清改成部分收款”之类的直接按钮。

| 当前收款状态 | 目标表现 | 是否允许 | 正确操作 | 条件 | 审批 |
|---|---|---:|---|---|---|
| `UNPAID` | 更早状态 | 否 | 无 | 已是初始状态 | — |
| `PARTIAL` | `UNPAID` | 有条件 | 冲销全部有效收款流水 | 没有已发货后的退款/售后冲突；冲销后重算为 0 | R2 |
| `SETTLED` | `PARTIAL` | 有条件 | 冲销部分收款或短款核销流水 | 指定原流水；冲销后余额大于 0 | R2 |
| `SETTLED` | `UNPAID` | 有条件 | 冲销全部有效收款及核销流水 | 所有依赖校验通过 | R2 |
| 任意状态 | 金额纠错但状态不变 | 允许 | 冲销错误流水，再录入正确流水 | 原流水未被冲销；金额守恒 | R2 |

以下行为禁止：

- 直接更新 `paid_amount`、`write_off_amount`、`balance_amount` 或 `collection_status`。
- 删除收款、核销、退款或冲销流水。
- 用取消订单代替现金退款。
- 用修改订单总额伪装退款或核销。

### 5.3 履约状态与履约方式

| 当前履约状态/方式 | 可逆动作 | 回退结果 | 必须满足的条件 | 审批等级 |
|---|---|---|---|---|
| `CONFIRMED / UNDECIDED` | 无需回退 | 保持当前状态 | 尚未选择履约方向 | — |
| `WAITING_ALLOCATION / STOCK_LINKED` | 撤销履约选择 | `CONFIRMED / UNDECIDED` | 没有有效配货计划、出库单、库存流水和售后单 | R0 |
| `ALLOCATING / STOCK_LINKED` | 取消配货方案 | `WAITING_ALLOCATION / STOCK_LINKED` | 方案未确认、没有出库事实；计划改为已取消并保留 | R0 |
| `READY_TO_SHIP / STOCK_LINKED` | 撤销配货确认 | `ALLOCATING / STOCK_LINKED` | 尚未出库；没有下游发货、退货或盘点引用 | R1 |
| `SHIPPED / STOCK_LINKED` | 冲销出库 | `READY_TO_SHIP / STOCK_LINKED` | 精确反向库存可执行；无售后、二次出库、锁定结账期等依赖 | R2 |
| `COMPLETED / STOCK_LINKED` | 撤销完成 | `SHIPPED / STOCK_LINKED` | 没有售后、发票锁定、业绩结算或已关闭期间 | R1 |
| `COMPLETED / RECORD_ONLY` | 撤销仅记录完成 | `CONFIRMED / UNDECIDED` | 没有库存事实、售后、发票锁定或已关闭期间 | R1 |
| `CANCELLED` | 禁止恢复 | 复制为新订单 | 取消可能已经关联退款和审计事实 | R3 |

说明：

- `COMPLETED / STOCK_LINKED` 如果要恢复到待发货，需要先“撤销完成”回到 `SHIPPED`，再单独申请“冲销出库”。不能一步跨过库存事实。
- `ALLOCATING` 取消方案后，如果最终想改成仅记录订单，还要继续执行“撤销履约选择”，回到 `CONFIRMED / UNDECIDED` 后重新选择。
- 占位 SKU 的拆分不随履约回退自动合并。拆分错误应通过独立明细修订保留前后记录。

### 5.4 取消、退货和售后

| 情况 | 是否允许状态回退 | 正确处理 |
|---|---:|---|
| 未发货订单想终止 | 不需要回退 | 取消订单；已收款仍需单独退款或保留应退状态 |
| 已发货但实际未发出 | 不直接改状态 | 申请冲销出库，生成反向库存事实 |
| 客户已经收到货并退回 | 否 | 创建销售退货单，验收入库并处理退款 |
| 客户换货 | 否 | 创建换货/退货关系，不回写原销售事实 |
| 已取消后发现取消错误 | 否 | 复制原订单生成新订单，并关联来源 |

“撤销出库”和“销售退货”必须区分：

- 撤销出库表示原出库事实本身录错或实际没有发生。
- 销售退货表示原销售和出库真实发生，之后又产生新的退回事实。

## 六、每个逆向动作的事务契约

### 6.1 撤销履约选择

动作编码建议：`undoFulfillmentDecision`

```text
WAITING_ALLOCATION / STOCK_LINKED
  → CONFIRMED / UNDECIDED
```

执行要求：

1. 锁定订单并校验租户、数据范围、版本和幂等键。
2. 确认不存在有效配货计划、出库单、库存流水及待审批逆向申请。
3. 不修改订单商品、金额、收款状态、财务流水和占位 SKU 拆分记录。
4. 清空当前有效的 `fulfillment_decided_at/by`；原选择保留在状态转换日志中。
5. 同事务更新新状态字段和旧兼容字段。
6. 写入原因、操作人、来源和前后状态。

页面完成后重新显示“关联库存”和“仅记录订单”两个选择。

### 6.2 取消配货方案

动作编码建议：`cancelAllocationPlan`

```text
ALLOCATING → WAITING_ALLOCATION
```

执行要求：

- 配货计划改为 `CANCELLED`，记录取消人、取消时间和原因。
- 调整记录、原仓库选择和原数量永久保留，不能物理删除。
- 当前有效计划查询排除已取消版本。
- 再次创建配货计划时生成新版本，不覆盖已取消版本。
- 没有库存预留或库存流水时不产生库存反向记录。

当前代码中的 `cancelAdjustment()` 会删除配货计划和调整记录，实施本设计时必须先改成只追加/软取消模型。

### 6.3 撤销配货确认

动作编码建议：`reopenAllocation`

```text
READY_TO_SHIP → ALLOCATING
```

执行要求：

- 确认没有任何出库单或库存流水。
- 配货计划从 `ALLOCATED` 回到可编辑状态，保留上一次确认人、时间和版本。
- 新修改形成下一版本或明确的调整日志。
- 由审批通过后的执行事务再次检查订单版本，防止审批期间已经发货。

### 6.4 撤销仅记录完成

动作编码建议：`reopenRecordOnlyOrder`

```text
COMPLETED / RECORD_ONLY
  → CONFIRMED / UNDECIDED
```

执行要求：

- 必须确认订单从未产生配货计划、出库单和库存流水。
- 收款状态和财务流水保持原样。
- 没有已生效售后、发票锁定、业绩结算或关闭期间。
- 回退后可重新选择 `RECORD_ONLY` 或 `STOCK_LINKED`。

### 6.5 撤销完成

动作编码建议：`reopenCompletedOrder`

```text
COMPLETED / STOCK_LINKED → SHIPPED / STOCK_LINKED
```

该动作只撤销“流程完成标记”，不撤销出库，不修改库存。需要进一步撤销出库时，必须另外提交“冲销出库”申请。

### 6.6 冲销出库

动作编码建议：`reverseShipment`

```text
SHIPPED → READY_TO_SHIP
```

执行要求：

1. 读取原出库单及每个仓库/SKU/数量。
2. 写入引用原出库流水的反向库存流水，不删除原记录。
3. 恢复库存快照并保持仓库、SKU、数量逐项守恒。
4. 原出库单标记为 `REVERSED`，记录对应冲销单号。
5. 订单和配货计划退回待发货口径。
6. 任一 SKU 恢复失败，全部订单、库存、计划和日志一起回滚。

如果商品已经实际退回，应使用销售退货，不使用冲销出库。

### 6.7 财务流水冲销

动作沿用：`reverseFinancialRecord`

执行要求：

- 只能冲销未被冲销的原始流水，不能冲销 `REVERSAL`。
- 新增一条引用原流水的反向记录，原流水不修改、不删除。
- 重算实收、退款、核销、尾款和 `collection_status`。
- 审批通过时重新校验订单版本、原流水状态及金额不变量。
- 履约状态原则上不随财务冲销自动倒退；如需要改变履约方向，另走履约回退动作。

## 七、禁止回退和必须阻断的条件

以下任一条件成立时，普通回退必须被拒绝或升级为专门冲销/售后流程：

1. 目标订单不是当前租户数据，或操作人不在订单数据范围内。
2. 订单属于未完成新模型迁移的历史异常行。
3. 订单版本已变化，审批所依据的状态和当前状态不一致。
4. 已存在另一条相同动作的待审批或执行中申请。
5. 存在有效出库单、库存流水，但用户发起的是普通状态回退。
6. 存在退货、换货、退款、发票、核销、佣金或结账期依赖，且当前动作没有处理该依赖。
7. 会计期间、库存期间或经营数据已经锁定。
8. 回退会导致库存、财务、订单金额或数量不守恒。
9. 原始记录已经被冲销、取消或由其他动作替代。
10. 用户试图跨越多个业务事实一步退回，例如 `COMPLETED/STOCK_LINKED` 直接退到 `CONFIRMED`。
11. 用户未填写回退原因，或高风险动作未完成审批。
12. Agent Key、外部 API 或批量脚本尝试调用回退接口。首版回退只允许登录后台人工发起和审批。

## 八、操作人与权限设计

权限最终由权限码和数据范围共同决定，不只依赖角色名称。建议新增：

| 权限码 | 说明 |
|---|---|
| `btn:order:rollback:request` | 发起订单回退申请 |
| `btn:order:rollback:route` | 执行未过账的履约路径纠错 |
| `btn:order:rollback:allocation` | 取消或重新打开配货方案 |
| `btn:order:rollback:shipment` | 发起/执行出库冲销 |
| `btn:order:rollback:finance` | 发起财务冲销 |
| `btn:order:rollback:approve` | 审批普通订单回退 |
| `btn:order:rollback:approveInventory` | 审批库存冲销 |
| `btn:order:rollback:approveFinance` | 审批财务冲销 |
| `btn:order:rollback:viewAudit` | 查看完整回退与审批记录 |

默认角色矩阵建议：

| 角色 | 路径纠错 | 配货撤销 | 出库冲销 | 财务冲销 | 审批权限 |
|---|---|---|---|---|---|
| `ROLE_OWNER` 老板 | 可执行 | 可执行/审批 | 可审批 | 可审批 | 全部审批，R2 不得审批本人申请 |
| `ROLE_ADMIN` 系统管理员 | 可执行 | 可执行 | 可发起，不默认审批 | 可发起，不默认审批 | 仅普通回退；高风险需显式额外授权 |
| `ROLE_SALES` 销售员 | 仅本人订单可申请 | 不执行 | 不执行 | 仅本人订单可申请纠错 | 无 |
| `ROLE_WAREHOUSE` 仓库管理员 | 可对可见订单执行 R0 | 可执行/申请 | 可申请和执行已批准请求 | 无 | 无 |
| `ROLE_FINANCE` 财务 | 可查看影响 | 无 | 无 | 可申请和执行已批准请求 | 不得审批本人申请 |
| `ROLE_PURCHASE` 采购 | 无 | 无 | 无 | 无 | 无 |

后端必须同时校验：

- 当前租户；
- 按钮权限；
- `OrderAccessPolicy` 数据范围；
- 申请人和审批人是否允许为同一人；
- 订单当前状态和下游依赖。

前端隐藏按钮不能代替后端鉴权。

## 九、动作与审批矩阵

| 动作 | 默认发起人 | 默认执行人 | 默认审批人 | 自批 | 等级 |
|---|---|---|---|---:|---|
| 撤销履约选择 | Owner/Admin/Warehouse | 原操作人 | 无 | 可 | R0 |
| 取消未确认配货方案 | Owner/Admin/Warehouse | 原操作人 | 无 | 可 | R0 |
| 撤销配货确认 | Warehouse/Admin/Owner | Warehouse/Admin | Owner | Owner 强验证例外可配置 | R1 |
| 撤销仅记录完成 | Sales/Admin/Owner | Admin/Owner | Owner | Owner 强验证例外可配置 | R1 |

## 十、审批流程

### 10.1 标准流程

```text
申请人选择逆向动作
  → 服务端返回影响预览和阻断原因
  → 填写原因并提交
  → 生成 PENDING 审批申请
  → 审批人查看前后状态、库存/财务影响和关联单据
  → 批准或拒绝
  → 批准后重新锁单并校验版本与依赖
  → 执行逆向事务
  → 写状态日志、审批日志、反向流水和缓存失效事件
  → 标记 EXECUTED
```

审批通过不等于无条件执行。审批期间如果订单已经发货、退款或被其他人修改，执行时必须判定申请已过期，状态改为 `STALE`，要求重新申请。

### 10.2 审批状态

| 状态 | 含义 |
|---|---|
| `PENDING` | 等待审批 |
| `APPROVED` | 已批准，等待执行或正在执行 |
| `REJECTED` | 已拒绝 |
| `CANCELLED` | 申请人撤回 |
| `STALE` | 订单状态或版本已变化，申请失效 |
| `EXECUTED` | 逆向事务完成 |
| `FAILED` | 执行失败，未产生部分结果 |
| `EXPIRED` | 超过有效期未处理 |

### 10.3 审批数据模型建议

新增只追加审批主表 `order_rollback_request`：

| 字段 | 说明 |
|---|---|
| `id / tenant_id / order_id` | 主键、租户和订单 |
| `action` | 申请的明确逆向动作 |
| `from_status / to_status` | 申请时的履约状态前后值 |
| `from_mode / to_mode` | 履约方式前后值 |
| `financial_impact` | 是否影响财务事实 |
| `inventory_impact` | 是否影响库存事实 |
| `impact_snapshot_json` | 申请时影响预览，不保存密钥等敏感信息 |
| `reason` | 必填原因 |
| `risk_level` | R0/R1/R2/R3 |
| `policy_version` | 使用的审批策略版本 |
| `order_version` | 申请时订单版本 |
| `status` | 审批状态 |
| `requested_by/at` | 申请人和时间 |
| `approved_by/at/opinion` | 审批人、时间和意见 |
| `executed_by/at` | 实际执行人和时间 |
| `idempotency_key` | 防止重复提交和执行 |
| `failure_code/message` | 执行失败原因 |

另建只追加明细表 `order_rollback_approval_log`，保存每次提交、批准、拒绝、撤回、失效、执行和失败事件。不得通过覆盖主表字段替代完整审批轨迹。

## 十一、页面交互

### 11.1 订单详情页

不提供“修改状态”下拉框。页面根据后端 `allowedActions` 显示明确按钮：

- 撤销履约选择
- 取消配货方案
- 撤销配货确认
- 撤销完成
- 申请冲销出库
- 申请财务冲销

### 11.2 影响预览

点击逆向动作后必须先显示：

- 当前状态与目标状态；
- 保持不变的内容，例如已收金额和订单明细；
- 会被取消或冲销的配货计划、出库单、库存流水、财务流水；
- 是否需要审批、审批人范围和预计失效时间；
- 当前阻断原因；
- 必填回退原因。

R0 使用红色或橙色二次确认后直接执行。R1/R2 的主按钮应写“提交回退申请”，不能写“确认回退”。

### 11.3 审批中心

订单管理下新增“订单回退审批”列表：

- 待我审批；
- 我发起的；
- 已执行；
- 已拒绝/已失效；
- 按订单号、动作类型、风险等级、申请人和时间筛选。

审批详情必须能跳转到原订单、原配货计划、原出库单和原财务流水。

## 十二、API 边界

建议接口：

```text
GET  /api/orders/{id}/rollback-options
POST /api/orders/{id}/rollback-preview
POST /api/orders/{id}/rollback-requests
GET  /api/orders/rollback-requests
GET  /api/orders/rollback-requests/{requestId}
POST /api/orders/rollback-requests/{requestId}/approve
POST /api/orders/rollback-requests/{requestId}/reject
POST /api/orders/rollback-requests/{requestId}/cancel
```

约束：

- 请求只提交动作和原因，不提交任意目标状态值。
- R0 可以在提交请求后由服务端同事务直接执行并返回 `EXECUTED`。
- R1/R2 先生成申请，审批通过后由统一执行器执行。
- 所有写接口要求幂等键。
- 审批接口重新验证权限、申请人分离、订单版本和依赖。
- 首版不向 Agent Key 开放任何回退、审批、冲销接口。

## 十三、日志、统计和其他系统联动

### 13.1 状态与审批日志

- `order_state_transition_log` 继续记录履约状态、收款状态和履约方式前后值。
- 新增动作编码必须纳入统一动作枚举和日志展示。
- 审批日志与状态日志通过 `rollback_request_id` 关联。
- 配货计划、出库单和财务流水保留原记录及反向记录。

### 13.2 统计

- 订单销售额按有效正式订单及业务日期统计，不因未涉及金额的履约回退重复计算。
- 现金统计以未被冲销的财务流水为准。
- 库存统计以原流水和反向流水净额为准。
- 已完成订单数量在撤销完成后应减少，在重新完成后恢复。
- 审批中的申请不改变任何经营统计，只有 `EXECUTED` 后才生效。

### 13.3 缓存、导出和多端

执行成功后统一失效：

- 订单详情与列表缓存；
- 客户贡献和偏好缓存；
- Dashboard/Analytics 聚合缓存；
- 库存及库存预警缓存；
- PC、移动端和共享类型中的 `allowedActions`。

导出必须显示当前有效状态，并可选显示最近一次回退动作、原因和审批人。移动端首版只读展示审批状态，不提供 R2 高风险执行入口。

## 十五、实施顺序

### 第一阶段：未出库路径纠错（优先）

1. 建立回退动作枚举、权限、影响预览和统一依赖检查器。
2. 实现 `WAITING_ALLOCATION → CONFIRMED/UNDECIDED`。
3. 重构取消配货方案，停止物理删除计划和调整记录。
4. 实现 `READY_TO_SHIP → ALLOCATING`。
5. 实现 `COMPLETED/RECORD_ONLY → CONFIRMED/UNDECIDED`。
6. PC 页面增加明确的逆向按钮、影响预览和原因输入。

第一阶段不产生反向库存或财务流水，最适合先上线验证。

### 第二阶段：审批底座

1. 新增回退申请和审批日志表。
2. 实现 R1/R2、职责分离、申请失效和防重复执行。
3. 增加审批中心及站内待办。
4. 财务冲销接入 R2 审批。

### 第三阶段：库存逆向

1. 出库单与库存流水增加冲销引用。
2. 实现逐仓库、逐 SKU 反向库存事务。
3. 实现 `SHIPPED → READY_TO_SHIP`。
4. 与盘点、退货、库存结账期建立依赖检查。

### 第四阶段：售后和订单修订

1. 独立销售退货、换货和退款流程。
2. 正式订单修订版本和差异审计。
3. 发票、佣金、应收子账及关账期联动。

## 十六、测试与发布门禁

### 16.1 状态机

- 每个允许转换都有正向测试。
- 每个不允许跨级回退都有反例测试。
- 新旧状态兼容字段必须同事务一致。
- 历史未迁移行不得进入新回退状态机。

### 16.2 权限和审批

- 跨租户、无权限、越权访问他人订单必须返回 403。
- SALES 只能申请本人数据范围内订单。
- R2 申请人不能审批自己的申请。
- 审批期间订单版本变化时申请必须变为 `STALE`。
- 重复提交、重复批准和并发执行只能成功一次。

### 16.3 财务与库存不变量

- 冲销前后财务流水可重算订单快照。
- 原库存流水 + 反向流水净额与库存快照一致。
- 多 SKU 冲销任一失败时全部回滚。
- 回退履约不得修改实收、核销和订单金额。
- 审批拒绝、撤回或失效不得产生业务副作用。

### 16.4 发布

- 数据库只做加法迁移，不删除现有字段和历史记录。
- 生产副本完成迁移、审批、回退、并发和失败回滚预演。
- 发布前备份数据库；应用回滚不依赖数据库降级。
- 首发只开放第一阶段的未出库回退；库存冲销通过独立开关启用。
- 上线后核对订单、财务、库存、配货计划和状态日志总量守恒。

## 十七、锁定决策

1. 不开发任意状态编辑器。
2. 正式订单不能退回草稿。
3. 已取消订单首版不能恢复，只能复制新单。
4. 履约回退不自动撤销财务事实。
5. 已出库后不能直接改状态，必须冲销库存或走销售退货。
6. 配货计划和调整记录停止物理删除，改为取消/版本化。
7. R0 必填原因并二次确认；R1/R2 进入审批流程。
8. R2 强制申请人与审批人分离。
9. Agent Key 首版不得调用任何回退、审批或冲销接口。
10. 所有逆向动作由后端状态机计算结果，并写入不可变审计轨迹。
