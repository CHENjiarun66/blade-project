## 按改动类型选择发布流程

| 改动 | 发布要求 |
|---|---|
| 纯文档、任务或归档 | 提交/同步 Git，不部署应用 |
| 无 schema 改动的应用修复 | 最新正式代码基线、相关测试、真实身份/接口冒烟、不可变 amd64 镜像、可回滚旧镜像与 jar、备份及发布前后校验 |
| 新 migration / 数据回填 | 另做隔离生产副本演练、明确起止版本/数据影响/人工核对/恢复方案，再执行授权的发布计划 |
| uploads 迁移、覆盖或数据恢复 | 单独说明数据范围和风险，按该次授权与备份计划操作 |

`deploy/nas/deploy_app_from_local.sh` 当前仍是订单大迁移专用流程：默认目标 V58，要求旧迁移演练证据，并执行 `OrderLegacyMigrator`。它还没有收口为通用的 V69 日常发布器，不能把历史命令原样用作每次热修复的默认操作。普通应用发布与数据迁移拆分见改进任务 `BE-STAB-005`；在脚本改造前必须先审查具体执行计划。

2026-11-01 两次无迁移修复使用已记录的独立发布脚本，只替换 backend 并 reload Nginx。该记录是已执行操作的证据，不是授权以后任意版本绕过测试或备份。

## 备份与回滚边界

- 发布前保留数据库、schema、SHA-256 和 NAS 外副本；现有备份工具为 `deploy/nas/backup_db.sh`
- 数据库、uploads、TLS 私钥和运行密钥不能用本机开发文件覆盖
- 日常应用发布只操作需要更新的应用容器，保持 MySQL/Redis 的容器与数据目录
- 应用回滚优先使用旧应用镜像；数据库恢复、删除、回填属于独立数据操作
- 不执行 `docker-compose down -v`、volume prune 或删除生产数据目录
- 保存发布 manifest、完整源码 SHA、镜像 SHA、备份路径、验证结果及维护模式状态

任何发布都要按用户在当前会话中的授权范围执行，不重复索要已经给出的授权，也不把一份历史提示词当作本次生产变更指令。
